# Notes for Claude Code

## Goal and hard rules
- Add-on for DreamPi (Raspberry Pi bridge for the Sega Dreamcast modem) that routes calls to DC Now or DCNet.
- **Never modify DreamPi's own files** (`/home/pi/dreampi/dreampi.py`, `netlink.py`, `dcnow.py`). DreamPi auto-updates them from GitHub, and the add-on must install and uninstall cleanly without touching them.
- `netswitch_hook.py` runs inside DreamPi, which runs on **Python 2.7**. Keep it Python 2 and 3 compatible: no f-strings, no type hints, no Python-3-only stdlib. The web page runs separately under Python 3.

## Naming in the UI
User-facing text (web page, README, log lines) spells the networks **DCNow!** and **DCNET**; the buttons read "DCNow! / DreamPi" and "DCNET / FLYCAST". Code identifiers, file names and upstream strings keep their original spelling (`dcnow`, `dcnet`, `[DCNet]` in `netlink_config.ini`, DreamPi's `DCNet Call answered` log text).

## How it works
- `install.sh` copies files to `/opt/dreampi-netswitch`, writes `dreampi_netswitch.pth` into site-packages for `python`, `python2` and `python3` (the list is kept in `pth_locations`), creates and starts the `dreampi-netswitch` systemd service (web page), and restarts the `dreampi` service. It also copies `netswitch_gpio.py` (shared low-level GPIO register access, see below) and `netswitch_wifi.py`, but only creates/starts the `dreampi-netswitch-wifi` service with `--wifi`; see [Wi-Fi setup button](#wi-fi-setup-button).
- The `.pth` file imports `netswitch_hook`. It only acts when `/proc/self/cmdline` contains `dreampi` (`sys.argv` doesn't exist yet during `.pth` processing on Python 2). It then temporarily wraps `__import__`, using `__builtin__` before `builtins` because python-future can provide a fake `builtins` on Python 2. When a module named `netlink` is imported from `/home/pi/dreampi`, it wraps `Netlink.check_number()` and restores the original `__import__`.
- State lives in files: `/opt/dreampi-netswitch/dcnet_mode` (exists means DCNet is selected), `/opt/dreampi-netswitch/autoreset` (reset toggle) and `/opt/dreampi-netswitch/default_dcnet` (exists means auto reset returns to DCNet instead of DC Now; page: `POST /default`). The hook writes `/tmp/dreampi-netswitch.active` (`active pid=N` or an error). The hook also writes `/tmp/dreampi-netswitch.state` (`starting`, `ready`, `call <network>` or `unknown`, plus a unix time): `starting` when netlink is imported, `call ...` from `check_number()`, and `ready` after `__main__.Modem.start_dial_tone()` (the moment DreamPi logs `<LISTENING>`) or `Netlink.reset_serial()`. The web page checks that pid under `/proc`, and also reads `netlink_config.ini` and `/boot/noautoupdates.txt` to warn when DCNet is off.
- Modem status: the hook adds a `logging.Handler` to DreamPi's `dreampi` logger and maps DreamPi's own messages (`<LISTENING>`, `Heard:`, `CONNECT 33600`, `Call answered`, `Connected`, `Detected modem hang up`, ...) to a short text in `/tmp/dreampi-netswitch.modem` (`<unix time> <text>`). Table `_MODEM_EVENTS`; keep it in sync if upstream log texts change. The same table's `Opening serial interface to (\S+)` row also writes the raw port (e.g. `/dev/ttyUSB0`) to `/tmp/dreampi-netswitch.port`, which is how the web service finds the modem without guessing or parsing `netlink_config.ini`.
- Modem identification (`netswitch_web.py`) is **passive only**: nothing is ever sent to the modem, and DreamPi is never stopped or restarted. `modem_port()` reads that port file; `_usb_info(port)` is a pure sysfs read (`/sys/class/tty/<tty>/device`, walked up to the `idVendor`/`idProduct`/`manufacturer`/`product`/`serial` files), never touches the modem, and is how `modem_plugged()` (the port path exists) and the make/model label come from. `modem_compat(usb)` matches the USB descriptor's manufacturer+product string against `KNOWN_MODEMS`/`UNKNOWN_MODEMS` (only "descriptor contains the known name", never the other way round, or a short bad entry like `conceptronic c56u` would match the longer good `conceptronic c56u-v2` as a substring); the list and its source (a DreamPi modem-compatibility forum thread) are comments above `KNOWN_MODEMS`, expected to grow. `api_state()`'s `modem.plugged`/`label`/`compat` and a "not detected" / "known not to work" warning box come from the same functions; `about()` adds a Modem row with the label and compatibility note. An earlier version also actively probed the modem over the serial port (`ATI`/`AT+GM*`) to show its firmware, stopping and restarting `dreampi.service` around it; on real hardware that left DreamPi stuck re-opening the serial port ("Opening modem on ..." never clearing) instead of completing, so it was removed - see git history (`probe_modem`/`run_modem_check`/`start_modem_check`, removed) before reviving anything like it, and test against real hardware first.
- HTTPS: `install.sh` makes a self-signed certificate (`https.crt`/`https.key` in `/opt/dreampi-netswitch`, SAN `dreampi.local`, `<hostname>.local`, the Pi's IPv4 addresses; 820 days because Apple rejects > 825; renewed by the installer when < 30 days are left) with `openssl req -config` (no `-addext`, for older OpenSSL). The web service is started as `netswitch_web.py <http port> <https port>` (443 by default, `0` = off, `--https-port=N` / `--no-https`). The HTTPS server runs in a second thread; the TLS handshake happens in each request's thread (`finish_request`), so a browser sitting on the certificate warning can't block the accept loop. If the certificate is missing or the port is taken, HTTP keeps working. Both servers are threading (`ThreadingMixIn`).
- The web page works on Python 3 and 2.7. It serves a static page that polls `GET /api` (JSON) every 1 s; buttons POST via XMLHttpRequest (plain form POST + 303 still works without JS). A background thread checks internet every 30 s. The debug panel is hidden behind a "Debug log" toggle button, and that button itself only shows when "Debug log" is ticked under Network in the settings (per browser, `localStorage` key `netswitch-debug`); the log is only polled while it is open. The selected-network box (`#net`, class `now rows`) also holds the status: closed it shows the network name and, centred underneath, the DreamPi status dot and text (the DreamPi label hidden); clicking it adds class `open`, which shows the DreamPi label and the Modem, Internet and Pi rows. `render()` keeps `open` when it updates the network class. Rows keep their first line on one line (`.nw`, ellipsis if too long) with a smaller second line (`.sub.blk`: modem "3 min ago", Pi uptime + IP). With the Dreamcast background the box turns translucent grey with its network-coloured border, like the Dreamcast BIOS pop-ups (the user wants it that way). A cogwheel opens a full-screen settings overlay (`#settings`) holding the Default network switch, Auto reset, the phone-number table, Appearance and the Status LED settings (`#led-section`, shown only when `led_enabled` exists, i.e. installed with `--led`).
- Page styling: colours are CSS variables in `:root` (`--dcnow`, `--dcnet` and lighter `-l` variants). One corner radius `--r` (29px) for all big boxes and buttons. Main buttons are `.pill` (network colour with a 5px lighter border); the status box, selected-network box, warnings and the full-width `.wide` Debug log button share that shape, small buttons `.pill-s`, settings groups `.card` with `.srow` rows, and every checkbox (Auto reset, Dreamcast background, Follow) uses the one `.cbox` style. Buttons and the Default network switch are slightly translucent (rgba) so the optional background shows through. The cogwheel and close icons are inline SVGs in `#3a3a3a`. In the LED table, the colour swatch, effect chip and level chip are all 30px tall; tabs pick the network; `#fx-pop` and `#lvl-pop` (class `.pop`) are the pop-up menus. The status dot previews the effect with CSS animations (`DOT_FX`).
- Dreamcast background (optional, off by default, per browser via `localStorage` key `netswitch-bg`): `static/dc-background.js` is Robert Dale Smith's `background.js` from RobertDaleSmith/vmu-icon-maker (MIT), wrapped as `window.DCBackground.start(el)/stop()`, without his performance toggle and clock, pausing on `visibilitychange`. `static/three.min.js` is Three.js r128 from the same repo. The page loads both lazily when the switch is on and adds `dcbg` to html and body. His blue gradient is painted on the fixed `#dcbg` layer itself (100lvh, translateZ), not with `background-attachment: fixed`, which iOS Safari ignores; the script sizes the canvas from that container and ignores small height-only resizes (mobile toolbars). Tab icons: `static/favicon-dcnow.png` / `favicon-dcnet.png` (64 px, transparent) and `touch-*.png` (180 px on #111, apple-touch-icon), made from images the user supplied (DreamPi logo cropped above its text; the purple Flycast logo); the page swaps `#fav`/`#touch` when the selected network changes. `GET /static/<name>` serves only the files listed in `STATIC_FILES` (cached a day); `install.sh` copies `static/`. Credits and licences: README "Credits" and `static/LICENSES.txt` (the user wants credit in the README, not on the page).
- Web service robustness: listens dual-stack (`::` with IPV6_V6ONLY off, falls back to IPv4) because phones often try the IPv6 address of dreampi.local first; `request_queue_size` 64; `Handler.timeout` 20 s; every request runs through `_safely()` (500 + traceback in the journal instead of a dropped connection); `watchdog()` GETs `/ping` every 20 s and exits after 3 failures so systemd restarts it (`Restart=always`, `RestartSec=3`, `StartLimitIntervalSec=0`, Nice=-5). The page and static files are kept in memory with their gzip; the page's own POSTs send `X-Requested-With` and get 204 instead of a 303 + full page. `wifi-powersave-off.sh` runs as `ExecStartPre` and switches Wi-Fi power saving off (it resets on reboot).
- Hang up (`POST /hangup`, button at the bottom of the open network box, tap twice; the row `#hang-row` only shows, and the server only acts, while `dreampi_state()` starts with `call`): `force_hangup()` in a thread ends the call the way DreamPi does: `pkill -TERM -x pppd` (dreampi.py's CONNECTED loop waits for pppd's "Exit" in /var/log/messages, then sends +++ ATH0 and restarts the dial tone) and `pkill -TERM -f dcnet.rpi` (netlink's `dcnet_connect()` polls for it, then reconnects the modem and starts the dial tone). If `dreampi_state()` isn't `ok` within 30 s, or nothing was running, it runs `systemctl restart dreampi.service`. Progress in `/api` `hangup`, the debug log and the journal. No DreamPi files are touched.
- Pi health (`pi_health()`, sampled every 2 s in `checker()`): CPU % from /proc/stat deltas, RAM from /proc/meminfo (MemAvailable), temperature from thermal_zone0, uptime, and the firmware's throttled flags (`/sys/devices/platform/soc/soc:firmware/get_throttled`, else `vcgencmd get_throttled`, at most every 10 s; bit 0 under-voltage now, 1 capped, 2 throttled, 16/18 since boot). State bad = under-voltage/throttled now or >= 80 °C (LED message `pi`, warning box), warn = since boot or >= 70 °C. `/api` gives `line1` (CPU, RAM, temp; kept on one line), `line2` (uptime, LAN IP from `lan_ip()`: the source address of a UDP socket "connected" to 192.0.2.1, no packet sent) and `warn`. Shown as the Pi row, `pi=` in /status, `pi_problem` in the net state file.
- Versions (`about()`, `GET /about`, About card in settings): DreamPi's scripts carry `#dreampi.py_version=YYYYMMDDhhmm` / `#netlink_version=...` lines that its updater compares; there is no image version file. The add-on version is written to `/opt/dreampi-netswitch/version` by install.sh (git date + short hash of the checkout).
- Network detection (web service, `checker()`): `link_state()` every 2 s reads `/sys/class/net` (Ethernet = eth*/en* with carrier, Wi-Fi = wireless iface up) and `/proc/net/route` (default route, not via ppp/tun/lo, = "network"); `internet_checker()` runs in its own thread (30 s while OK, 5 s while failing, immediately when links change). Both go to `/tmp/dreampi-netswitch.net` (JSON, atomic), which the LED service reads via `network_state()` (ignored when older than 20 s). No network / no internet also add a warning box on the page.
- LED messages: `LED_STATES` lists every message highest priority first with its category and defaults: category `wifi` (highest priority, see [Wi-Fi setup button](#wi-fi-setup-button)): `wifi-setup`, `wifi-ok`, `wifi-failed`; then errors `no-network`, `no-internet`, `pi`, `off`, `unknown`; information `busy`, `call-dcnow`, `call-dcnet`, `call`, `ok`, `ethernet`, `wifi` (the last two off by default; note the category "wifi" for the setup messages and the message key "wifi" for "Wi-Fi connected" are unrelated, unfortunate as that overlap is). `active_messages()` returns the enabled ones that apply now (DreamPi state + network state + `wifi_state()`, unless called with `wifi=False`), lowest priority first; the LED service's `render()` draws them in that order into each message's section (`leds` null = all, else [first, last] 1-based, clipped to the strip), so more important messages end up on top and uncovered LEDs stay dark. `status_look()` = the top one (currently unused; `api_state()` builds the dot preview straight from `active_messages()`). The page's DreamPi dot previews only the DreamPi-state message (`active_messages(state, {"network": True}, wifi=False)` - `wifi=False` so it never shows the Wi-Fi setup colour there, only in warning boxes and the real LED).
- LED/status colours: `/opt/dreampi-netswitch/led.json` = `{"brightness": 0..1 (default 0.08; the page slider is logarithmic, base 100, 0-1000 steps), "order": "GRB"|"RGB"|"RBG"|"GBR"|"BRG"|"BGR" (wire order, most WS2812s are GRB), "calibrate": {<column>: {<row>: "#rrggbb" | null}} (the 9x3 swatch grid, see below), "colours": {"dcnow"|"dcnet": {<state>: {"color": "#rrggbb", "effect": solid|blink|breathe|rgb|rainbow|scanner|comet|chase|twinkle, "speed": slow|fast, "brightness": null | 0..1, "enabled": bool, "leds": null | [first, last]}}}}` (per-status `brightness` null = use the global brightness; `status_look()` returns the effective value, which the LED uses), keyed by the *selected* network (`dcnet_mode`) and the `dreampi_state()` value. `netswitch_web.led_config()` fills in defaults and validates; `save_led_config()` writes atomically (tmp + rename). `GET /ledconfig` returns config, defaults, state labels, `orders`, `calib_columns`/`calib_rows`/`calib_swatches`, whether `led_enabled` exists and whether `hidden` (see below); `POST /ledconfig` takes the whole config as JSON plus extra `count`/`gpio` fields (see Status NeoPixels) that aren't part of the saved JSON. `status_look()` gives the current colour/blink; `/api` includes it as `dreampi.look`, and the page's DreamPi dot uses it (inline background + `blink` class), so the dot previews the LED.
- Colour calibration (`netswitch_web.py`: `CALIB_HUES`/`CALIB_COLUMNS`/`CALIB_ROWS`/`CALIB_LIGHTNESS`/`calib_swatch()`; `netswitch_led.py`: `calib_table()`/`calib_offset()`): the settings page shows a 9 (hue: red, orange, yellow, green, cyan, blue, purple, magenta, white) x 3 (lightness: light, medium, dark) grid of reference swatches, computed server-side with `colorsys.hls_to_rgb` (white = zero saturation). Tapping one opens R/G/B sliders (0..255) that drive the LED live (see below) so the page's swatch and the physical LED can be compared directly; whatever the user settles on is saved as that cell's `"#rrggbb"` (`null` = uncalibrated, i.e. no correction). `calib_table(cfg)` turns each calibrated cell into an offset (`calibrated - reference`, per channel, in -255..255) and leaves uncalibrated cells at `(0,0,0)`; `calib_offset(table, r, g, b)` (0..255 in) finds the colour's hue/lightness/saturation (`colorsys.rgb_to_hls`), interpolates the offset circularly across the 8 hue columns at that lightness (`_hue_interp`/`_row_interp`; the 8 hues aren't evenly spaced, matching how far apart they look), does the same for the "white" column using only lightness, and blends the two by saturation - so a fully saturated colour gets the hue-interpolated correction, a grey one gets white's, and anything in between blends smoothly rather than jumping at a cutoff. Below the "dark" row (lightness 0.25) `_row_interp()` fades the offset down to no correction at all by lightness 0, rather than clamping to the dark row's full offset - a fully-off/black pixel (blink's off-phase, breathe's trough, an unlit strip section) must never be tinted by a dark-row calibration, which is also most of what's on screen at the default 8% global brightness. `to_bytes()` computes each pixel's pre-calibration 0..255 value, adds this offset, clamps, then dithers/quantizes as before. This generalises the LED's correction the same way from any swatch that's been matched to every other colour the LEDs show (including in-between hues from the rainbow effect and the lightness a breathing status slides through), and - unlike a flat per-channel gain - can add a channel back in from zero (a pure hue swatch has two channels at exactly 0, where a gain could never do anything), which is needed to fix a wrong-looking hue rather than just an overall wash-out.
- Calibration live preview: while the popup is open, the page POSTs the slider RGB to `/calibpreview` (debounced ~100 ms on every slider move, plus a 1 s heartbeat from `openCalib()` that resends the current sliders even while they're untouched, so the preview file doesn't go stale during a long side-by-side comparison) and `POST /calibdone` when it closes (the popup only closes on an explicit outside click, Escape, or Done - there is no auto-close timer). `web.calib_preview()` returns that colour while it's no older than `CALIB_PREVIEW_STALE` (3 s, so a closed/crashed tab stops driving the LED on its own) else `None`. The LED service's main loop checks it every `REFRESH` tick alongside everything else it reads from the page, and while it's set shows that flat colour directly (no effects, no calibration correction - that's what's being figured out) instead of calling `render()`.
- Hiding the LED settings: `/opt/dreampi-netswitch/led_hidden` (exists = hidden), toggled by `POST /ledhide` from a "Hide" button inside `#led-section` (with a confirm dialog, since there is no way back from the page itself - the button that hides the section is inside the section it hides). Meant for shipping a product with the LEDs already configured and keeping end users from changing them by accident; only reversible by deleting the file on the Pi (or reinstalling). `loadLed()` hides `#led-section` when either `installed` is false or `hidden` is true.

## Status NeoPixels
`netswitch_led.py` (Python 3, service `dreampi-netswitch-led` running as root, installed with `install.sh --led` (1 LED) or `--leds=N` (1-300, just the *starting* count, stored in `/opt/dreampi-netswitch/led_count`), remembered via `led_enabled`, removed with `--no-led`) drives WS2812s on one of four pins (`GPIO_PINS` = 10, 12, 18, 21; `DEFAULT_GPIO` = 18), stored in `/opt/dreampi-netswitch/led_gpio` (`install.sh --led-gpio=N`, also editable from the page) with no driver or Python package, except on GPIO10. GPIO12 and GPIO18 are the PWM0 peripheral (only the pin's ALT function differs: ALT0 vs ALT5); GPIO21 is the PCM peripheral (PCM_DOUT, ALT0), the same technique through different registers, used so GPIO12/18 (or the audio jack, which also uses PWM) stay free; GPIO10 is hardware SPI0 (MOSI) through the kernel's own `spidev` character device instead of `/dev/mem`, needing `dtparam=spi=on` (which `install.sh --led-gpio=10` adds to `/boot/firmware/config.txt` or `/boot/config.txt`, tracked in `spi_added` the same way the old SPI-on-GPIO10 versions were, so switching away removes it again; needs a reboot either way). For PWM/PCM: maps the GPIO, clock-manager and peripheral register blocks from `/dev/mem` (`netswitch_gpio.peripheral_base()`, reading `/proc/device-tree/soc/ranges`; 32-bit accesses through `netswitch_gpio.Block`, `ctypes.c_uint32.from_buffer` - that module is shared with `netswitch_wifi.py`'s button reading, each service opens its own `/dev/mem` mapping since they're separate processes), sets the pin's ALT function and clocks the peripheral from the crystal (19.2 MHz / 8 = 2.4 MHz; Pi 4: 54 MHz / 22) via `_init_clock()` (shared between PWM's and PCM's clock-generator offsets, `CM_PWMCTL`/`CM_PWMDIV` vs `CM_PCMCTL`/`CM_PCMDIV` - same register layout, BCM2835), serialiser mode, 3 output-clock ticks per LED bit (`100` = 0, `110` = 1), wire order from `led.json` (default GRB, matching the old hardcoded order), MSB first (`_TABLE` maps a byte to 3 bytes; `ORDERS` maps the 6 permutations to which of `(r, g, b)` goes out 1st/2nd/3rd, kept on the output object as `.order`).
- 1 LED on GPIO12/18 (`FifoPixel`): 3 words written straight into the FIFO; the pin idles low when it empties (`RPTL1` off), which latches.
- Anything else on GPIO12/18/21 (`DmaStrip` for PWM, `PcmStrip` for PCM, sharing `_DmaOutput`'s `show()`/close via `_dma_setup()`/`_dma_close()`): like rpi_ws281x. GPU memory from the VideoCore mailbox (`_alloc_gpu()`/`_free_gpu()`: `/dev/vcio`, `_IOWR(100,0,char*)`; tags 0x3000C alloc (flags 0x4 on Pi 2+, 0xC on Pi 1), 0x3000D lock -> bus address, 0x3000E/F unlock/release on exit), mapped through `/dev/mem` at `bus & ~0xC0000000`. Control block at offset 0 (TI = NO_WIDE_BURSTS|WAIT_RESP|DEST_DREQ|SRC_INC, PERMAP 5 for PWM's FIF1 (0x7E20C018) or 2 for PCM's fifo (0x7E203004)), data after it: the encoded stream byte-swapped per 32-bit word (both peripherals shift MSB first) plus 24 zero words (reset). DMA channel 10. PWM: PWM_DMAC = ENAB|PANIC 7|DREQ 3. PCM: `cs=EN`, `mode=FLEN(31)|FSLEN(1)`, `txc=CH1WEX|CH1EN|CH1POS(0)|CH1WID(8)`, `cs|=TXCLR`, `cs|=DMAEN`, `dreq=TX(0x3F)|TX_PANIC(0x10)`, `cs|=TXON` (register values cross-checked against github.com/jgarff/rpi_ws281x's pcm.h/ws2811.c, not from a datasheet or hardware). Each frame: wait for the channel, write data, reset channel, load CONBLK_AD, start.
- GPIO10 (`SpiStrip`): opens `/dev/spidevB.D` directly (mode/speed via `fcntl.ioctl`, no `spidev` package), ~6.4 MHz (the Pi rounds to 6.25 MHz). One whole SPI *byte* is one NeoPixel bit (`SPI_ONE`=0xF8, `SPI_ZERO`=0xC0, `_SPI_TABLE`), since spidev only deals in whole bytes; `show()` is a single blocking `os.write()`, no DMA. This is what the add-on's own older versions did on this exact pin (`git show 479cb3b:netswitch_led.py`), generalised here to any LED count, wire order and calibration.
- Single LED on GPIO18 verified on hardware; the DMA strip path (any peripheral/pin) only against fake memory/mailbox, and GPIO12/21/10 not at all.
- Loop: 50 fps; re-reads `web.calib_preview()` and `web.active_messages()` every 0.25 s and, unless previewing (see Colour calibration above), composes the messages with `render(messages, now, count, clocks, calib)`. Each message's effect restarts at t=0 when it appears or its look changes (`clocks`), so blink starts lit and breathe starts bright. Unchanged frames are only resent every 0.5 s (CPU). The service runs at Nice=10. `effect_frame(effect, speed, colour, t, n)` gives floats per LED; `to_bytes()` applies brightness, then the calibration offset table (see Colour calibration above; `None` = no correction), then quantizes to 0..255 with temporal (error-diffusion) dithering: the rounding error is carried over per (LED index, channel) and added to the next frame, so a value 8-bit output can't represent exactly - the normal case at low brightness, where slow effects like breathe would otherwise visibly step between levels - is approximated by alternating the neighbouring levels over time instead of always rounding the same way; `reset_dither()` clears that carried-over state. The main loop also re-reads `web.led_config()` (`order`, `calibrate` via `calib_table()`), `web.led_count()` and `web.led_gpio()` every 0.25 s; a changed count or pin opens the new hardware output *before* closing the old one (falls back to keeping the current output, logged to stderr, if the new one fails to open - e.g. GPIO10 chosen without SPI enabled) so the LED count and output pin can both be changed from the page without a restart, and a failed switch can't leave the service stuck on a closed output. Effects: solid, blink, breathe, rgb (20 s slow / 10 s fast; rainbow the same) for any count; rainbow, scanner, comet, chase, twinkle for strips (on 1 LED they fall back to rgb/breathe/blink-like output). Periods per effect in `PERIODS` (slow, fast).
- Older versions used SPI on GPIO10 and added `dtparam=spi=on  # added by dreampi-netswitch` (recorded in `spi_added`); the installer and uninstaller remove only that line - the current SPI path (`SpiStrip`, above) is the same idea, generalised to any LED count/order/calibration.

## Wi-Fi setup button
`netswitch_wifi.py` (Python 3, service `dreampi-netswitch-wifi` running as root, installed with `install.sh --wifi` (enables the button; default GPIO17 / physical pin 11, written to `wifi_button_gpio` only if that file doesn't already exist, so a manually-edited pin survives updates - GPIO15 was the original default but shares the Pi's UART RX function and got reports of unreliable presses, possibly from serial/Bluetooth activity on that line; GPIO17 has no other function on any Pi model), remembered via `wifi_button_enabled`, removed with `--no-wifi`). Lets the Pi join a Wi-Fi network without a keyboard/monitor: hold the button 3 s (or use Settings > Network > Wi-Fi setup, or POST `/wifitoggle`, on the main page), and the Pi hosts a temporary access point with a page to pick a network - the same network list and Connect flow also appears in the regular page's Settings while it's up (see below). **Not yet verified on real hardware** (see below); it's built to fail safe (every system-changing call is wrapped and best-effort) but everything about it is unverified except the pieces shared with the already-verified LED code (`netswitch_gpio`).

- **Button:** a background thread maps the pin with `netswitch_gpio.set_input_pullup()` (internal pull-up; idle high, low while pressed - BCM2711/Pi 4 uses `GPIO_PUP_PDN_CNTRL_REG0`, older Pis the classic `GPPUD`/`GPPUDCLK0` sequence) and polls `read_level()` every `BUTTON_POLL` = 10 ms. The two pull registers encode up/down the opposite way round from each other (each per its own Broadcom datasheet): `GPIO_PUP_PDN_CNTRL_REGx` is 01=up/10=down, classic `GPPUD` is 01=down/10=up. A first pass on real hardware (a Pi 3, the classic path) wrote the same constant (1) to both, which is pull-up on Pi 4 but pull-DOWN on a Pi 3 - with the button wired to GND and no external resistor, that reads permanently low whether pressed or not ("the button doesn't work"). Fixed with separate, correctly-named constants per path (`PI4_PULL_UP`/`PI4_PULL_DOWN` vs `GPPUD_PULL_UP`/`GPPUD_PULL_DOWN`); never reuse one pull-direction constant across both registers again.
  - **Debounce:** the raw level is only trusted once it reads the same for `DEBOUNCE_SAMPLES` (3) samples running (~30 ms) - a `candidate`/`candidate_count` pair separate from the confirmed `stable` level. Without this, a single physical press could register as several quick press/release pairs from contact bounce: at best two toggles cancelling out, at worst the short/long-press timing landing right on a threshold ("works, but not reliably" - found from real hardware, same as the pull-up bug above).
  - A debounced press-start resets `pressed_since`/`fired`; while held, a continuous `HOLD_SECONDS` = 3 s low fires once (`fired` latch) and touches the same trigger files the web page's button does - see below - so both share one code path (`_start_wifi_toggle()`). A debounced release that never fired and was held at least `SHORT_PRESS_MIN` = 30 ms calls `toggle_network()` instead: flips `web.FLAG` (`dcnet_mode`), the same file the web page's DCNow!/DCNET buttons and the special phone numbers use - a quick tap switches networks, holding it is Wi-Fi setup.
  - `main()` falls back to `DEFAULT_GPIO` (17) if `wifi_button_gpio` is ever missing/unreadable, matching install.sh's default. GPIO17 replaced an original default of GPIO15, which doubles as the Pi's UART RX and got reports of unreliable presses (serial console / Bluetooth activity is a plausible noise source on that line); GPIO17 has no other function on any Pi model.
- **Control files** under `/opt/dreampi-netswitch`: `wifi_start` / `wifi_stop`, touched by the button thread or by `POST /wifitoggle` (`netswitch_web.py`; toggles based on `wifi_state()["state"]`, mirroring the button's own idle-check) and consumed by the main loop, which clears both every iteration. `wifi_connect` (JSON `{"ssid":..., "password":...}`) is the same idea for choosing a network: `POST /wificonnect` on the *regular* page writes it, and `run_ap_server()`'s wait loop (`check_external_connect()`) polls for it alongside the AP page's own `/connect`, so either page can supply the connect action - this is what lets the network list also work from Settings on the regular page when it's reachable some other way (e.g. Ethernet) while Wi-Fi is mid-setup, not only by joining the temporary AP. All three files are deliberately the *only* things the button/either page share literally (not a function call - separate processes), matching every other cross-process control in this add-on (`dcnet_mode`, `autoreset`, ...).
- **State file** `/tmp/dreampi-netswitch.wifi` (JSON: `state`, `ssid`, `networks` while hosting, unix `time`), written by `set_state()` on every transition and re-read by `netswitch_web.wifi_state()` (idle if missing, or if `state != "idle"` and stale past `WIFI_STALE` = 30 s - the service crashed mid-setup). Consumed by `api_state()`'s `wifi` field (now including `networks`, so the regular page's Settings can render the same list) and warnings, and by `active_messages()` for the LED (`wifi=True` by default; `wifi=False` for the DreamPi-dot-only call).
- **The cycle** (`setup_cycle()` / `_setup_cycle()`, looping until stopped or connected): `scanning` -> `wpa_cli scan` + `scan_results` (`scan_networks()`, deduplicated by SSID keeping the strongest signal, `secured` from the WPA/WEP flags; empty list on any failure, either page still allows a manual SSID) -> `hosting` -> `start_ap()` stops `wpa_supplicant`/`dhcpcd` on the interface, gives it `192.168.4.1/24`, writes `wifi_hostapd.conf` / `wifi_dnsmasq.conf` and starts both as child processes (`hostapd`, `dnsmasq -C ... --no-daemon`, no captive-portal detection beyond `dnsmasq`'s `address=/#/192.168.4.1` and answering common OS probe paths) -> `run_ap_server()` serves the setup page on `192.168.4.1:80` (own `BaseHTTPRequestHandler`, blocks on a `queue.Queue` for `/connect` or `/stop`, also polling `check_external_connect()` for `wifi_connect`) -> `connecting` -> `try_connect()` calls `restore_client()`, writes the network into `/etc/wpa_supplicant/wpa_supplicant.conf` (`save_network()`: replaces any existing block for the same SSID, `_network_block()` shells out to `wpa_passphrase` and strips its plaintext `#psk=` comment; an empty password writes `key_mgmt=NONE`), `wpa_cli reconfigure`, then polls for an IP (`has_ip()`) within `CONNECT_TIMEOUT` = 25 s and finally `web.check_internet()` -> `ok` (green, `RESULT_PAUSE` = 5 s, done) or `failed` (red, 5 s, loops back to `scanning`). A stop request (file or button) is checked throughout (`wait_or_stop()`, `stop_requested()`) and always ends in `restore_client()` + `idle`. The regular page only shows the network list/Connect UI during `scanning`/`hosting` (`showNets` in `render()`) - not `connecting`, since by then the AP (and its `/connect` and `wifi_connect` polling) is already torn down.
- **Graceful exit:** SIGTERM/SIGINT (service stop, `uninstall.sh`, reboot) call `_graceful_exit()`, which tears down the AP and restores client Wi-Fi if a cycle was in progress (`_active_iface`), the same pattern `netswitch_led.py` uses for its LEDs on the same signals - without it, stopping the service mid-setup would strand the interface in AP mode.
- **AP page** (`_ap_page()` / `AP_STYLE` / `AP_SCRIPT` / `AP_PAGE_TMPL`): a small self-contained page (not sharing `netswitch_web.PAGE` - different process, and that page's CSS is delicately tuned and hardware-verified, not worth the risk of entangling) that reuses the same look (dark theme, `--r` pill radius, translucent blue accent). Lists scanned networks (signal shown as block characters), a manual-entry button for hidden SSIDs, a password field shown only for secured networks, Connect and Cancel.
- **Regular page's copy of the network list** (`netswitch_web.py`, Settings > Network, `#wifi-networks`): renders from `d.wifi.networks` in the same `/api` poll everything else uses, guarded by a `JSON.stringify` key comparison (`wifiListKey`) so the 1 s poll doesn't keep replacing the list/clobbering an in-progress password entry once it's already been rendered once per scan. `POST /wificonnect` (JSON body) is the only new server endpoint; it just writes `wifi_connect`, mirroring `/wifitoggle`'s file-touch pattern rather than duplicating any connect logic.
- **Assumes** the classic Raspberry Pi OS stack: `wpa_supplicant` + `dhcpcd` for the client side, `hostapd` + `dnsmasq` for the AP (installed via `apt` by `install.sh` if missing; their own systemd units are disabled so they don't fight the ones this service starts by hand). A NetworkManager-based image would need different code; nothing here touches it, so the rest of the add-on stays unaffected.
- The button's 3-second hold and the "hold again to cancel" behaviour, the AP name "DreamPi WiFi Config", green/red result and re-hosting on failure all come directly from the user's request; keep them if this is reworked. Same for the default GPIO17/pin11 (moved off GPIO15), surfacing the network list in the regular page's Settings too, and the short-press network toggle.

## Debug log
If `/opt/dreampi-netswitch/debug_dtmf` exists, the hook writes one timeline to `/tmp/dreampi-netswitch-dtmf.log` (`HH:MM:SS.mmm  +Nms  text`):
- modem bytes read while `modem._sending_tone` is true, decoded by `_serial_feed()`: `<DLE><digit>` -> `modem: DTMF x`, other `<DLE>` codes via `_DLE_CODES` (V.253), text lines -> `modem says: ...`. The hook replaces `read` on the pyserial object again after every `start_dial_tone()`, since DreamPi opens a new serial object after each call;
- every message on DreamPi's `dreampi` logger (`dreampi: ...`), via the same handler as the modem status;
- the number `check_number()` received (`add-on: number heard ...`) and routing lines.
The web service trims the log to its newest 500 KB whenever it passes 1 MB (`trim_log()` in the checker loop; safe because the hook opens the file per line). `GET /dtmf` serves the newest 256 KB (`?all` for everything). Responses over 2 KB are gzip-compressed when the browser accepts it. The web page appends its own actions (`web page: ...`), serves new text incrementally at `GET /log?from=<byte offset>` (JSON; `reset` when the file was cleared), shows it live in a panel polled every 0.7 s, and has `POST /debug` (toggle) and `POST /clearlog`. The page's status poll runs every 1 s. Note the page's HTML/JS lives in a Python string: write `\\n` for a JavaScript `\n`.

Open question being investigated: on hardware DreamPi heard openMenu's `1111111` as `11111111`, `1111` and `1`. Known contributors: (1) `digit_parser()` in netlink.py reads the digit right after `<DLE>` on a non-blocking port (`timeout=0`); if the byte hasn't arrived yet the digit is dropped and parsing restarts at the next `<DLE>` (reproduced in simulation). (2) openMenu's KallistiOS `modem_dial()` dials immediately after opening the line, without waiting for dial tone, using the modem chip's default DTMF timing. The debug log on real hardware decides which it is. Do not paper over it in the routing rules; the user wants the cause fixed.

## Upstream facts the hook depends on (netlink.py, dpi2 branch)
- `check_number(self, raw_string)` returns `{'client': mode, 'dial_string': ...}`. `dreampi.py` answers with its own pppd only when `client == 'PPP'`. Any other non-idle mode is handled by `Netlink.poll()` -> `mode_handler()`.
- Mode `"dcnet"` makes `mode_handler()` call `dcnet_connect()`, which answers and runs `dcnet.rpi`. This is the same route the built-in `*69` prefix uses: it stores `self.dial_modifier` in memory, valid for 10 seconds.
- `self.dcnet` is True only when `netlink_config.ini` has `[DCNet] enabled = yes` and `dcnet.rpi` exists.
- The serial-port path (`serial_poll`) also calls `check_number()` and handles `"dcnet"`.
- openMenu 1.7.0 always dials `1111111` with login `openMenu`/`openMenu` (see `dcnow_net.h` in DerekPascarella/openMenu-Virtual-Folder-Bundle). DCNet expects the password `password`, so `1111111` must stay on DC Now.
- If upstream renames `check_number`, the hook writes an error to the status file and does nothing, and DreamPi keeps working.

## Routing rules (see README table)
Special numbers are matched with `endswith()` on the dialed string: on real hardware DreamPi hears an extra leading `1` (e.g. `13333333` with the old DCNet number, `11111111`), and ISP prefixes add digits too. Only calls the original `check_number` returns as `PPP` are redirected. Numbers ending in `1111111` or `5550001` (select DC Now) always stay PPP. `5550002` (select DCNet), or any number while `dcnet_mode` exists, becomes `dcnet` if `self.dcnet` is true. With `autoreset`, `1111111` first sets the selection to the default network (`default_dcnet`); the openMenu call itself still stays PPP.

Switch only: a dialed string ending in `#` (not starting with `#`) whose part before the `#` matches a special number only changes the selection (`5550001#` DC Now, `5550002#` DCNet, `1111111#` the default network) and returns `{'client': 'idle'}` (sets `self.mode = 'idle'`), so DreamPi doesn't answer, like `*70`. `_play_busy()` swaps `modem._dial_tone_wav` for a generated busy tone (480+620 Hz, 0.5 s on/off, 8-bit unsigned 8 kHz) for `BUSY_SECONDS` (4 s), then a timer restores the real dial tone (kept in `modem._netswitch_dial`, so quick repeats don't save the busy tone as the dial tone). Only done while `modem._sending_tone` is true. Whether the Dreamcast reacts to the busy tone is not yet verified on hardware.

`5550001`/`5550002` (555-0001/555-0002, the North American fictional-exchange prefix) replaced the original `2222222`/`3333333`: a run of seven identical digits is the hardest case for a DTMF decoder to count correctly (no frequency change marks a digit boundary, only a timing gap) - the same category of problem as the openMenu `1111111` mishearing above, but for numbers we actually control. `1111111` itself can't change (hardcoded in openMenu).

## Verified on hardware
- The hook loads and patches under DreamPi's real Python 2.7.
- A real DCNet call end to end via the DCNet number (`333-3333` at the time, now `555-0002`); the routing logic (`_special()`/`endswith()` matching, `dcnet_mode`, `dcnet_connect()`) is unchanged by the renumbering, only the literal digits matched.
- A single NeoPixel on GPIO18 (PWM FIFO path, `FifoPixel`).
- The modem status/port pipeline: on a real CDC-ACM modem (`/dev/ttyACM0`), DreamPi's own `Opening serial interface to ...` log line was correctly matched and shown as "Opening modem on /dev/ttyACM0", confirming `_MODEM_EVENTS` and `_write_port()` work on hardware the earlier simulation-only testing didn't cover. (This was also how the removed AT-probe's problem was found: it stopped DreamPi right after this message, and DreamPi got stuck re-opening the port on restart - see the modem identification note above.)

## Not yet verified
- The strip path (`DmaStrip`, PWM + DMA, `--leds=N` with N > 1); only tested against fake memory and mailbox.
- Whether port 80 is free on every DreamPi image.
- LED temporal dithering, wire order and the swatch calibration grid: the quantization/dithering math, the byte-order permutation and the hue/lightness/saturation interpolation (`calib_offset()`) are covered by plain Python tests (no hardware needed for those - confirmed a calibrated cell's offset applies in full at that exact hue/lightness, half-strength halfway to an uncalibrated neighbour, fades to no correction at all below the "dark" row down to true black, and not at all to a fully desaturated colour when only a hue column is calibrated), but whether breathe genuinely looks smoother, and whether matching swatches by eye against a real LED actually fixes a washed-out or wrong-looking colour, haven't been checked against a real strip. The user reported on real hardware that calibrating made ordinary (non-preview) colours look unreliable; root cause was `_row_interp()` clamping any lightness at or below the dark row to that row's full offset, which could tint a fully-off pixel - fixed to fade to zero by lightness 0, confirmed with plain Python tests, not yet reconfirmed against the real strip. The same report also found the calibration popup's live LED preview going stale after a few seconds of untouched sliders (the `CALIB_PREVIEW_STALE` safety timeout, with nothing refreshing it between slider moves) - fixed with a 1 s heartbeat while the popup is open; not yet reconfirmed on hardware either.
- Changing the LED count or output pin from the page at runtime (closing and reopening the hardware output without restarting the service).
- GPIO12, GPIO21 (`PcmStrip`) and GPIO10 (`SpiStrip`) entirely: GPIO18 is the only pin ever tried on real hardware. The PCM register values are cross-checked against rpi_ws281x's source, not a datasheet or a real PCM peripheral; the SPI approach is this add-on's own former default for GPIO10 (verified back then), generalised here to any LED count/order/calibration rather than re-tested as-is.
- Modem identification: the USB descriptor lookup (`_usb_info()`) is plain sysfs reads and should be safe, but is itself only tested in simulation, not against a real modem's actual sysfs layout (e.g. a CDC-ACM modem at `/dev/ttyACM0`). `KNOWN_MODEMS`/`UNKNOWN_MODEMS` come from a DreamPi forum thread the user pasted in, not first-hand testing here.
- Whether the Dreamcast reacts as expected to the busy tone from a switch-only (`#`) number.
- Everything in [Wi-Fi setup button](#wi-fi-setup-button): the button GPIO reading, `hostapd`/`dnsmasq` AP hosting, `wpa_supplicant.conf` writing and reconnecting, and the assumption that DreamPi's OS image uses `wpa_supplicant`/`dhcpcd` rather than NetworkManager. Only unit-tested off-hardware (scan-result parsing, `wpa_supplicant.conf` dedup/rewrite, LED default-effect selection, page rendering) - see the git history for what was checked and how before treating this as working. The button itself already had one real bug found on hardware (the classic-Pi pull-up/down register mixup, see `set_input_pullup()` in `netswitch_gpio.py`), now fixed but not yet reconfirmed on the Pi 3 that found it.
