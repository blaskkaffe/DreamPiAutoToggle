# Buttons, GPIO settings and Wi-Fi setup

Read before touching `netswitch_buttons.py`, `netswitch_wifi_setup.py` or the GPIO settings box. Back to [CLAUDE.md](../CLAUDE.md).

## GPIO settings box

- GPIO settings box (`#gpio-section`, Settings > GPIO, one `.card` styled like the Network card's `.srow` rows - a bold label, a grey one-line description, and the row's controls on the right, instead of the denser `.secrow` layout Status LED uses): one row per device, `#gpio-led-row` (LED: `led-count-i`/`led-gpio`/`led-order` - count, output pin and wire order, the same elements and `/ledconfig` save path as before, just relocated here from Status LED and still hidden with the rest of it when `led_hidden`), `#gpio-btn1-row`/`#gpio-btn2-row` (each button's function select then its pin select) and `#gpio-wifi-row` (the Wi-Fi-setup assignment), the buttons always shown, the Wi-Fi row only when `wifi_enabled` exists (`GET /buttonconfig` returns `wifi` for that). This keeps the GPIO box to purely physical/wiring settings (which pin does what, how many LEDs, their wire order) and Status LED to purely how things look (colour calibration, brightness, per-message colour/effect) - nothing wiring-related is left in Status LED. `button1_gpio`/`button2_gpio` (`BUTTON_GPIO_PINS` = any of GPIO2-27, no peripheral restriction the way the LED pins have) and `button1_function`/`button2_function` (`BUTTON_FUNCTIONS`: `off`, `toggle`, `dcnow`, `dcnet`) default to GPIO17/`toggle` and GPIO4/`off`; `wifi_button` (`WIFI_BUTTON_CHOICES`: `"1"`, `"2"`, `"12"`) - which button, or both held together, triggers the Wi-Fi-setup hold - defaults to `"1"`. `GET`/`POST /buttonconfig` (`netswitch_web.py`) mirror `/ledconfig`'s pattern; the POST only saves the two GPIO numbers if they differ from each other (two buttons can't share one physical pin), leaving both at their previous values otherwise. See [Buttons and Wi-Fi setup](buttons-wifi.md) for how `netswitch_buttons.py` turns these into button behaviour, and reads config changes live.

## Buttons and Wi-Fi setup

`netswitch_buttons.py` + `netswitch_wifi_setup.py` (Python 3, service `dreampi-netswitch-buttons` running as root, always installed (up to two buttons - default GPIO17/pin11, function "toggle network", and GPIO4/pin7, function "off"; install.sh seeds the pins) while the Wi-Fi setup half is only enabled by `install.sh --wifi`; pins, functions and which one(s) hold-to-start Wi-Fi setup all live in `button1_gpio`/`button2_gpio`/`button1_function`/`button2_function`/`wifi_button`, see GPIO settings box in this file's first section above - install.sh only seeds the two GPIO defaults if those files don't already exist, so a page-edited pin survives updates), Wi-Fi setup remembered via `wifi_enabled`, removed with `--no-wifi`, which leaves the buttons running; without `wifi_enabled`, `_button_config()` passes an empty Wi-Fi assignment so `check_wifi_hold()` never fires and `main()` skips the whole setup loop). Lets the Pi join a Wi-Fi network without a keyboard/monitor: hold the assigned button(s) 3 s (or use Settings > Network > Wi-Fi setup, or POST `/wifitoggle`, on the main page), and the Pi hosts a temporary access point with a page to pick a network - the same network list and Connect flow also appears in the regular page's Settings while it's up (see below). **Not yet verified on real hardware** (see below); it's built to fail safe (every system-changing call is wrapped and best-effort) but everything about it is unverified except the pieces shared with the already-verified LED code (`netswitch_gpio`).

- **Buttons:** one background thread maps both pins (or just one, if `button2_gpio` happens to equal `button1_gpio`) with `netswitch_gpio.set_input_pullup()` (internal pull-up; idle high, low while pressed - BCM2711/Pi 4 uses `GPIO_PUP_PDN_CNTRL_REG0`, older Pis the classic `GPPUD`/`GPPUDCLK0` sequence) and polls `read_level()` for each every `BUTTON_POLL` = 10 ms (`button_watcher()`). The two pull registers encode up/down the opposite way round from each other (each per its own Broadcom datasheet): `GPIO_PUP_PDN_CNTRL_REGx` is 01=up/10=down, classic `GPPUD` is 01=down/10=up. A first pass on real hardware (a Pi 3, the classic path) wrote the same constant (1) to both, which is pull-up on Pi 4 but pull-DOWN on a Pi 3 - with the button wired to GND and no external resistor, that reads permanently low whether pressed or not ("the button doesn't work"). Fixed with separate, correctly-named constants per path (`PI4_PULL_UP`/`PI4_PULL_DOWN` vs `GPPUD_PULL_UP`/`GPPUD_PULL_DOWN`); never reuse one pull-direction constant across both registers again.
  - **Debounce** (`debounce_poll()`, a plain function so it's testable without real GPIO hardware - see Testing below): a button's raw level is only trusted once it reads the same for `DEBOUNCE_SAMPLES` (3) samples running (~30 ms) - a `candidate`/`candidate_count` pair separate from the confirmed `stable` level, one of each per button. Without this, a single physical press could register as several quick press/release pairs from contact bounce: at best two toggles cancelling out, at worst the short/long-press timing landing right on a threshold ("works, but not reliably" - found from real hardware, same as the pull-up bug above).
  - A debounced press-start resets that button's `pressed_since`/`fired`. `check_wifi_hold()` (also a plain function) fires the Wi-Fi hold once a `HOLD_SECONDS` = 3 s low is seen on whichever button(s) `wifi_button` names: `"1"` or `"2"` watches that one button alone, `"12"` only fires once *both* have been held down together for that long (measured from whichever of the two presses started later), and marks both `fired` so neither also fires its own short-press function on release. Firing touches the same trigger files the web page's Wi-Fi setup button does - see below - so both share one code path (`_start_wifi_toggle()`).
  - A debounced release that never fired a hold and was held at least `SHORT_PRESS_MIN` = 30 ms calls that button's configured function (`button1_function`/`button2_function`, looked up in `_BUTTON_FUNCTIONS`): `off` (nothing), `toggle_network()` (flips `core.FLAG` - `dcnet_mode`, the same file the web page's DCNow!/DCNET buttons and the special phone numbers use), or `select_network("dcnow"/"dcnet")` (selects that network outright, idempotent - does nothing if it's already selected). A button assigned to `wifi_button` still runs its own function normally on a *short* press; only a press that actually held long enough to fire the Wi-Fi hold skips it.
  - `main()` re-reads `button1_gpio`/`button2_gpio`/`button1_function`/`button2_function`/`wifi_button` (`_button_config()`) every `HEARTBEAT` = 2 s and, if any changed, stops the running `button_watcher()` thread (a `threading.Event`) and starts a new one with the new values - the same "pick up page changes live, no service restart" pattern `netswitch_led.py` uses for its LED count/pin, just far simpler here since a GPIO input needs no DMA/mailbox tear-down. GPIO17 was the original single button's default because it has no other function on any Pi model (replacing GPIO15, which doubles as the Pi's UART RX and got reports of unreliable presses - serial console / Bluetooth activity is a plausible noise source on that line); GPIO4 was picked as the second button's default for the same no-other-function reason.
- **Control files** under `/opt/dreampi-netswitch`: `wifi_start` / `wifi_stop`, touched by the button thread or by `POST /wifitoggle` (`netswitch_web.py`; toggles based on `wifi_state()["state"]`, mirroring the button's own idle-check) and consumed by the main loop, which clears both every iteration. `wifi_connect` (JSON `{"ssid":..., "password":...}`) is the same idea for choosing a network: `POST /wificonnect` on the *regular* page writes it, and `run_ap_server()`'s wait loop (`check_external_connect()`) polls for it alongside the AP page's own `/connect`, so either page can supply the connect action - this is what lets the network list also work from Settings on the regular page when it's reachable some other way (e.g. Ethernet) while Wi-Fi is mid-setup, not only by joining the temporary AP. These files are deliberately the *only* things the button thread/either page share literally (not a function call - separate processes), matching every other cross-process control in this add-on (`dcnet_mode`, `autoreset`, ...).
- **State file** `/tmp/dreampi-netswitch.wifi` (JSON: `state`, `ssid`, `networks` while hosting, unix `time`), written by `set_state()` on every transition and re-read by `netswitch_core.wifi_state()` (idle if missing, or if `state != "idle"` and stale past `WIFI_STALE` = 30 s - the service crashed mid-setup). Consumed by `api_state()`'s `wifi` field (now including `networks`, so the regular page's Settings can render the same list) and warnings, and by `active_messages()` for the LED (`wifi=True` by default; `wifi=False` for the DreamPi-dot-only call).
- **The cycle** (`setup_cycle()` / `_setup_cycle()`, looping until stopped or connected): `scanning` -> `wpa_cli scan` + `scan_results` (`scan_networks()`, deduplicated by SSID keeping the strongest signal, `secured` from the WPA/WEP flags; empty list on any failure, either page still allows a manual SSID) -> `hosting` -> `start_ap()` stops `wpa_supplicant`/`dhcpcd` on the interface, gives it `192.168.4.1/24`, writes `wifi_hostapd.conf` / `wifi_dnsmasq.conf` and starts both as child processes (`hostapd`, `dnsmasq -C ... --no-daemon`, no captive-portal detection beyond `dnsmasq`'s `address=/#/192.168.4.1` and answering common OS probe paths) -> `run_ap_server()` serves the setup page on `192.168.4.1:80` (own `BaseHTTPRequestHandler`, blocks on a `queue.Queue` for `/connect` or `/stop`, also polling `check_external_connect()` for `wifi_connect`) -> `connecting` -> `try_connect()` calls `restore_client()`, writes the network into `/etc/wpa_supplicant/wpa_supplicant.conf` (`save_network()`: replaces any existing block for the same SSID, `_network_block()` shells out to `wpa_passphrase` and strips its plaintext `#psk=` comment; an empty password writes `key_mgmt=NONE`), `wpa_cli reconfigure`, then polls for an IP (`has_ip()`) within `CONNECT_TIMEOUT` = 25 s and finally `probes.check_internet()` -> `ok` (green, `RESULT_PAUSE` = 5 s, done) or `failed` (red, 5 s, loops back to `scanning`). A stop request (file or button) is checked throughout (`wait_or_stop()`, `stop_requested()`) and always ends in `restore_client()` + `idle`. The regular page only shows the network list/Connect UI during `scanning`/`hosting` (`showNets` in `render()`) - not `connecting`, since by then the AP (and its `/connect` and `wifi_connect` polling) is already torn down.
- **Graceful exit:** SIGTERM/SIGINT (service stop, `uninstall.sh`, reboot) call `_graceful_exit()`, which tears down the AP and restores client Wi-Fi if a cycle was in progress (`_active_iface`), the same pattern `netswitch_led.py` uses for its LEDs on the same signals - without it, stopping the service mid-setup would strand the interface in AP mode.
- **AP page** (`_ap_page()` / `AP_STYLE` / `AP_SCRIPT` / `AP_PAGE_TMPL`): a small self-contained page (not sharing `netswitch_web.PAGE` - different process, and that page's CSS is delicately tuned and hardware-verified, not worth the risk of entangling) that reuses the same look (dark theme, `--r` pill radius, translucent blue accent). Lists scanned networks (signal shown as block characters), a manual-entry button for hidden SSIDs, a password field shown only for secured networks, Connect and Cancel.
- **Regular page's copy of the network list** (`netswitch_web.py`, Settings > Network, `#wifi-networks`): renders from `d.wifi.networks` in the same `/api` poll everything else uses, guarded by a `JSON.stringify` key comparison (`wifiListKey`) so the 1 s poll doesn't keep replacing the list/clobbering an in-progress password entry once it's already been rendered once per scan. `POST /wificonnect` (JSON body) is the only new server endpoint; it just writes `wifi_connect`, mirroring `/wifitoggle`'s file-touch pattern rather than duplicating any connect logic.
- **Assumes** the classic Raspberry Pi OS stack: `wpa_supplicant` + `dhcpcd` for the client side, `hostapd` + `dnsmasq` for the AP (installed via `apt` by `install.sh` if missing; their own systemd units are disabled so they don't fight the ones this service starts by hand). A NetworkManager-based image would need different code; nothing here touches it, so the rest of the add-on stays unaffected.
- The 3-second hold and the "hold again to cancel" behaviour, the AP name "DreamPi WiFi Config", green/red result and re-hosting on failure all come directly from the user's request; keep them if this is reworked. Same for the default GPIO17/pin11 (moved off GPIO15), surfacing the network list in the regular page's Settings too, the short-press network toggle, and the later two-button generalisation (GPIO4/pin7 as button 2, per-button function, configurable Wi-Fi-hold assignment including "both together").

## Testing the button logic

The button debounce/hold logic (`debounce_poll()`/`check_wifi_hold()` in `netswitch_buttons.py`) is plain functions over a small state list, with no GPIO/`/dev/mem` access, so it's tested by feeding a scripted sequence of raw levels (held/released, bouncy transitions, a `HOLD_SECONDS`-long hold, both buttons held together for `"12"`) through them directly and a fake clock (`time.time` replaced), asserting which of `toggle_network()`/`select_network()`/`_start_wifi_toggle()` ends up called - no thread, real sleep or fake `/dev/mem` mapping needed.
