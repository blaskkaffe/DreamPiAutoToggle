# The web service and page

Read before touching `netswitch_web.py`, `netswitch_probes.py` or `page/`. Back to [CLAUDE.md](../CLAUDE.md).

## Page files and behaviour

- The page is a frame plus the layouts of the enabled **modules**: `page/index.html` (header, cog, `#warnings`, `#dash`, the Settings overlay with `#set-boxes`, `#bg`), `page.css` (the page kit: tokens, buttons, boxes, pop-ups, the roster), `page.js` (kit, hooks, `/api` loop), `widgets.js` (the layout engine, the standard widgets, the module picker) and `boot.js` (draws the layout and starts the loop last). `netswitch_web.build_page()` puts them into one document (kept in memory, gzipped on demand) and adds each enabled module's `layout.json` (as `window.LAYOUT`), `page.css` and `page.js`. Edit those files, not the Python.
- The page polls `GET /api` (JSON) every second and redraws only what changed (`setText` / `setHtml`: no flicker, little work on a phone); buttons POST via XMLHttpRequest (the page needs JavaScript). **This is how screens stay in step:** the check-in board is in every `/api` answer with a revision number, so what one screen changes the others show within a second, with no push channel to keep alive.
- **How the page appears (no pop-in):** `body.booting` hides the dashboard and the warnings (`opacity: 0`, layout kept, so widgets can measure themselves) until the first `/api` answer and the first answer of every data source that has no kept answer; the last answer of each data source is kept in the browser (`localStorage`) and drawn at once on the next visit. After 1.5 s the page is shown anyway.
- Page styling (the shared building blocks are the "page kit", see [modules.md](modules.md)): colours are CSS variables: the global palette of 16 colours (`--c-<id>`, `-l` lighter variants, `-rgb` triples; `core.colours_css()` is put before `page.css`) and the classes `.c-<id>` that make an element use one as its primary colour.
- The page works with any module deleted or switched off, all of them included (`OFF=all` in the demo server).

## Highlight, notices and time zones (base)

`/api` always has `highlight` (`{box id: why}`), `notices` (`[{"id", "text", "post"}]`) and `theme` (`{"highlight": "rainbow" | palette id}`); modules fill the first two in their `api()` (for a box that should stand out: nothing uses it at the moment). The page puts class `hl` on those dashboard boxes (`applyHighlight()` in `widgets.js`; the looks are in `page.css`: a neutral `plain` box turns its colour, a coloured one gets the rainbow edge or the glow) and draws the notices after the warning boxes (`render()` in `page.js`; the ✕ POSTs `{"id"}` to the notice's `post`). `GET`/`POST /highlight` is the form behind Settings > Appearance > Notification highlight (`core.HIGHLIGHT`, a file holding `rainbow` or a palette id).
The common time zone: `GET`/`POST /timezone` (the form widget's `{values: {zone}, options: {zones}, texts}`; `core.time_zone()` / `save_time_zone()`, the `time_zone` file; `""` = the Pi's own). The form is in Settings > About (the `system` module's layout); the clock reads it, other modules can too.

`netswitch_tz.py` (base, Python 3): the UTC offset of an IANA zone at a moment, with summer time (`offset()`, `local_to_utc()` for a wall-clock time), and `CITIES`, the list of cities and zones the page offers (`zone_options()`). It uses `zoneinfo` when the Python has it (3.9+) and otherwise reads the system's TZif files in `/usr/share/zoneinfo` itself: the transitions, and the POSIX TZ rule at the end of the file for later years. `tests/test_tz.py` checks the reader against `zoneinfo` (random times in every listed zone, 1990-2040) and the hour around each change; a sweep over all 498 zones of the development machine, 150 random times each from 1975 to 2045, gave the same answer every time. Renamed zones (`Europe/Kyiv` / `Europe/Kiev`) work under either name.

## Optional modules

Everything the page shows is a module in `modules/`, loaded by `netswitch_modules.py` and (except the always-on ones) switched and ordered in Settings > System > Modules. How they plug in (manifest, layout, widgets, colours, web entry, hooks, installer): [modules.md](modules.md). The check-in board and the contacts: [checkin.md](checkin.md).

## Reboot

`POST /reboot` (the **Reboot and Update module**, `modules/rebootupdate/`: the Reboot row of the System card; PIN-protected) reboots the whole Pi via `systemctl reboot` after 2 s so the answer gets out; the page then waits for `/ping` to come back and reloads.

## Updates (`modules/rebootupdate/netswitch_update.py`, Settings > System; part of the Reboot and Update module)

`GET /update` returns the cached check (never starts a check by itself: updates are only looked for when the user presses Check now; "Not checked yet" until then), `POST /update/check` forces one, `POST /update/start` updates. Both POSTs need the `X-Requested-With` header (the page's own requests): the update runs git and the installer as root, and a bare cross-site form post must not be able to start it. **Add-on check:** `install.sh` records `version_commit` (full hash), `src_dir` (the checkout) and `install_ports`; the repo/branch come from the checkout's `origin` URL and current branch (default `blaskkaffe/DreamPiAutoToggle`, `main`); the GitHub API gives the branch head and `compare/<local>...<head>` says ahead (update available), behind (this install is ahead of GitHub), diverged or unknown commit (local changes). **Update now** (only with a recorded git checkout): `update_script()` (validated values only, runs as root) does `git fetch origin <branch>` + `merge --ff-only FETCH_HEAD` as the checkout's owner (`runuser`) and then `sh install.sh <http port> --https-port=<n>` from the remembered ports; it is started with `systemd-run` (else `setsid`) so the installer's restart of this service doesn't kill it. Status `running`/`ok`/`failed` in `/tmp/dreampi-netswitch.update` (a finished result is only reported for 10 min), output in `.update.log`. In Settings > System the update controls are the last rows of the System card (`#upd-row` Updates/Check, the DreamPi note, `#upd-do-row` Update now, then `#upd-log`); `_log_tail()` returns the last 14 non-empty lines with colour codes, progress-bar rewrites (`\r`) and control characters removed and each line cut at 300 characters, and `renderUpdLog()` shows them as a small scrolling console (`.updlog`, monospace, wraps long lines inside the card, errors red, success green, follows the end while you are not scrolled up). The page polls through the restart and reloads on `ok`. Not verified on a Pi: the `systemd-run`/`runuser` path.

## Security (`netswitch_security.py`)

The web service runs as root. Checks done in `netswitch_web.py` before an action: `security.host_allowed()` on every request (Host must be an IP, `localhost`, a single-label or private-suffix name, the Pi's own host name, or a line in `allowed_hosts` (`core.ALLOWED_HOSTS`); a missing Host header from an HTTP/1.0 client passes; otherwise 421) against DNS rebinding; `security.post_allowed()` on every POST (`Origin`, else `Referer`, must name the request's own Host; the page's `X-Requested-With` header passes; with neither header nor Origin, or with a strict action, 403; only a same-site form post without the header is accepted, and never for the paths a module lists as `PROTECTED`: `/reboot` and `/update/start` from the Reboot and Update module, `/contacts/import` and `/contacts/active` from the Contacts module); for those, `security.check_pin()` with the `X-Netswitch-Pin` header when `core.ADMIN_PIN` exists (PBKDF2-SHA256 salted hash, mode 600, written only by `install.sh --pin` via `netswitch_security.py set`, 401 wrong/missing, 429 for 60 s after 5 wrong tries, a damaged file refuses everything). `GET /api` has `pin` (the page prompts once and keeps the PIN in memory only); Settings > About shows a PIN row. Responses carry `X-Frame-Options: DENY`, CSP `frame-ancestors 'none'; object-src 'none'; base-uri 'none'; form-action 'self'`, `nosniff`, `Referrer-Policy: same-origin`. `_body(limit)` clamps Content-Length (a negative one used to read until the timeout); **Settings lock:** Settings > Appearance can set, change and remove the PIN (`POST /pin`, the old PIN is asked for first; while none is set anybody on the network can set one, which is why `install.sh --no-pin` stays) and **Ask for the PIN to open Settings** (`POST /settings-pin`, `core.SETTINGS_PIN`): then the cogwheel asks for the PIN, and every POST that is not a module's `OPEN` path (a dashboard action) needs it too. **PIN pad:** the page asks for a PIN (before an update / reboot, to open a locked Settings, when setting a new one) in its own dialog (`askPin()` in `page/page.js`): round number keys 0-9, a field that also takes a keyboard (a PIN may hold other characters), OK / Enter, Esc or the cross to cancel; checked in `tests/ui/screen.js`. **Screen layout:** `GET`/`POST /screen`, `/screen/stretch`, `/screen/scale`, `/screen/drag`, `/screen/noscroll` (`core.screen_settings()`, `screen.json`): max columns for the dashboard and Settings, stretch, scale, rearrange, no scrolling; `POST /modules/dashboard-order` reorders the modules after a tile was dragged. **Update:** `origin_problem()` requires the checkout's `remote.origin.url` to match `ORIGIN_RE` (GitHub https/ssh) and equal `update_origin` (written by `install.sh` from the checkout; absent on older installs = accepted once, then recorded); the script fetches that exact URL (`U`) with `GIT_ALLOW_PROTOCOL=https:ssh` instead of the name `origin`, the branch may not start with `-` or contain `..`, the start is under a lock, and the status file/log are removed and recreated with `set -C`/`O_NOFOLLOW` so a planted symlink in `/tmp` isn't followed. `install.sh` writes the unit with `NoNewPrivileges=yes`, `ProtectSystem=full`, `ProtectControlGroups=yes`, `ProtectKernelModules=yes`, keeps `/opt/dreampi-netswitch` at mode 755. Tests: `tests/test_security.py`. **Not verified on a Pi:** the systemd sandbox directives (a unit that no longer starts would show in `journalctl -u dreampi-netswitch`), `--pin` prompting on a real terminal, and `systemd-run`/`runuser` with the pinned-URL fetch. Known gap: the other state files in `/tmp` still have predictable names.

## Service robustness, HTTPS

- HTTPS: `install.sh` makes a self-signed certificate (`https.crt`/`https.key` in `/opt/dreampi-netswitch`, SAN `<hostname>.local`, the Pi's IPv4 addresses; 820 days because Apple rejects > 825; renewed by the installer when < 30 days are left) with `openssl req -config` (no `-addext`, for older OpenSSL). The web service is started as `netswitch_web.py <http port> <https port>` (443 by default, `0` = off, `--https-port=N` / `--no-https`). The HTTPS server runs in a second thread; the TLS handshake happens in each request's thread (`finish_request`), so a browser sitting on the certificate warning can't block the accept loop. If the certificate is missing or the port is taken, HTTP keeps working. Both servers are threading (`ThreadingMixIn`).
- Web service robustness: listens dual-stack (`::` with IPV6_V6ONLY off, falls back to IPv4) because phones often try the IPv6 address of the .local name first; `request_queue_size` 64; `Handler.timeout` 20 s; every request runs through `_safely()` (500 + traceback in the journal instead of a dropped connection); `watchdog()` GETs `/ping` every 20 s and exits after 3 failures so systemd restarts it (`Restart=always`, `RestartSec=3`, `StartLimitIntervalSec=0`, Nice=-5). The page and static files are kept in memory with their gzip; the page's own POSTs send `X-Requested-With` and get 204 instead of a 303 + full page. `wifi-powersave-off.sh` runs as `ExecStartPre` and switches Wi-Fi power saving off (it resets on reboot).

## Measurements

`netswitch_probes.py` is small: `check_internet()` (reaches public DNS servers over TCP, then resolves a host name; nothing calls it at the moment), `lan_ip()` (the address on the default route, no packet sent) and `about()` (the rows of Settings > About: add-on version from `/opt/dreampi-netswitch/version`, address, the Pi's model and the OS). Nothing runs in the background any more.
