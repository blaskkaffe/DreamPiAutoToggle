# The web service and page

Read before touching `base_web.py` or `base/page/`. Back to [CLAUDE.md](../CLAUDE.md).

## Page files and behaviour

- The page is a frame plus the layouts of the enabled **modules**: `base/page/index.html` (header, cog, `#warnings`, `#dash`, the Settings overlay with `#set-boxes`, `#bg`), `page.css` (the page kit: tokens, buttons, boxes, pop-ups, the roster), `page.js` (kit, hooks, `/api` loop), `widgets.js` (the layout engine, the standard widgets, the module picker) and `boot.js` (draws the layout and starts the loop last). `base_web.build_page()` puts them into one document (kept in memory, gzipped on demand) and adds each enabled module's `layout.json` (as `window.LAYOUT`), `page.css` and `page.js`. Edit those files, not the Python.
- The page polls `GET /api` (JSON) every second and redraws only what changed (`setText` / `setHtml`: no flicker, little work on a phone); buttons POST via XMLHttpRequest (the page needs JavaScript). **This is how screens stay in step:** the check-in board is in every `/api` answer with a revision number, so what one screen changes the others show within a second, with no push channel to keep alive.
- **How the page appears (no pop-in):** `body.booting` hides the dashboard and the warnings (`opacity: 0`, layout kept, so widgets can measure themselves) until the first `/api` answer and the first answer of every data source that has no kept answer; the last answer of each data source is kept in the browser (`localStorage`) and drawn at once on the next visit. After 1.5 s the page is shown anyway.
- Page styling (the shared building blocks are the "page kit", see [modules.md](modules.md)): colours are CSS variables: the global palette of 16 colours (`--c-<id>`, `-l` lighter variants, `-rgb` triples; `core.colours_css()` is put before `page.css`) and the classes `.c-<id>` that make an element use one as its primary colour.
- The page works with any module deleted or switched off, all of them included (`OFF=all` in the demo server).

## Notices and time zones (base)

`/api` always has `notices` (`[{"id", "text", "post"}]`): a module fills it in its `api()` and the page draws the notices after the warning boxes (`render()` in `page.js`; the ✕ POSTs `{"id"}` to the notice's `post`). The notification highlight of dashboard boxes (`/highlight`, the `hl` class) was removed.
**Per-screen settings:** a request with `X-Screen: <id>` (`[A-Za-z0-9][A-Za-z0-9_-]{0,63}`; the page takes it from `?screen=<id>` and keeps it in `sessionStorage`) reads and writes that screen's own `screens/<id>/screen.json` and `tile_layout.json` (`core.set_screen()` per request thread; the shared files are the starting point; at most 200 screens; `build_page()` always uses the shared ones). `POST /screen/locations {value: [buildings]}` keeps a screen's building filter (ignored without an id); `/api` `screen.locations` carries it back. See [pxe.md](pxe.md).

The common time zone: `GET`/`POST /timezone` (the form widget's `{values: {zone}, options: {zones}, texts}`; `core.time_zone()` / `save_time_zone()`, the `time_zone` file; `""` = the computer's own). The form is in Settings > About (the `system` module's layout); the clock reads it, other modules can too.

`base/base_tz.py` (base, Python 3): the UTC offset of an IANA zone at a moment, with summer time (`offset()`, `local_to_utc()` for a wall-clock time), and `CITIES`, the list of cities and zones the page offers (`zone_options()`). It uses `zoneinfo` when the Python has it (3.9+) and otherwise reads the system's TZif files in `/usr/share/zoneinfo` itself: the transitions, and the POSIX TZ rule at the end of the file for later years. `tests/test_tz.py` checks the reader against `zoneinfo` (random times in every listed zone, 1990-2040) and the hour around each change; a sweep over all 498 zones of the development machine, 150 random times each from 1975 to 2045, gave the same answer every time. Renamed zones (`Europe/Kyiv` / `Europe/Kiev`) work under either name.

## Optional modules

Everything the page shows is a module in `modules/`, loaded by `base/base_modules.py` and (except the always-on ones) switched and ordered in Settings > System > Modules. How they plug in (manifest, layout, widgets, colours, web entry, hooks, installer): [modules.md](modules.md). The check-in board and the contacts: [checkin.md](checkin.md).

## Reboot

`POST /reboot` (the **Reboot and Update module**, `modules/rebootupdate/`: the Reboot row of the System card; PIN-protected) reboots the whole computer after 2 s so the answer gets out; the page then waits for `/ping` to come back and reloads. The web service is not root: `rebootupdate_web._spawn_reboot()` runs `systemctl start --no-block checkin-board-reboot.service`, a root-owned oneshot unit (written by `modules/rebootupdate/install.sh`) whose command is `sleep 2; systemctl --no-block --ignore-inhibitors reboot`; a polkit rule lets the service user start that unit. Where that is refused the page says "Could not reboot (...)".

## Updates (`modules/rebootupdate/rebootupdate_update.py`, Settings > System; part of the Reboot and Update module)

**Update from USB** (`rebootupdate_update.usb_candidates()` / `start_usb_update()`, `POST /update/usb`, protected like `/update/start`): the folders called `update` on mounted drives (`USB_ROOTS`: `/media/*`, `/media/*/*`, `/run/media/*/*`, `/mnt/*`, `/mnt/*/*`; a link is not followed) that have `install.sh`, `base/base_web.py` and `modules/` are listed in `GET /update` as `usb` (the page shows the newest). The root updater (`update-run.sh usb`, see below) looks for the stick itself with the same patterns (a stick mounted so that only the desktop user can read it, which is how some desktops mount, is invisible to the page, which is an ordinary user, and only the updater sees it; give the service that user with `install.sh --user=` if that is your case), copies the newest folder to `<install folder>/usb_src` (root-owned) and runs its `install.sh` with `NS_KEEP_SRC=1` (the recorded checkout and its commit / origin are left alone, the commit record is removed) and `NS_VERSION` ("USB update <date of install.sh>"); log and status are the same files as the GitHub update. Not tried with a real stick or a real automount. `GET /update` returns the cached check (never starts a check by itself: updates are only looked for when the user presses Check now; "Not checked yet" until then), `POST /update/check` forces one, `POST /update/start` updates. Both POSTs need the `X-Requested-With` header (the page's own requests): the update runs git and the installer as root, and a bare cross-site form post must not be able to start it. **Add-on check:** `install.sh` records `version_commit` (full hash), `src_dir` (the checkout) and `install_ports`; the repo/branch come from the checkout's `origin` URL and branch as install.sh recorded them (`update_origin`, `update_branch`; default `blaskkaffe/CheckinChicken`, `main`); the GitHub API gives the branch head and `compare/<local>...<head>` says ahead (update available), behind (this install is ahead of GitHub), diverged or unknown commit (local changes). **Update now** (only with a recorded git checkout): `update_script()` (validated values only, runs as root) does `git fetch origin <branch>` + `merge --ff-only FETCH_HEAD` as the checkout's owner (`runuser`) and then `sh install.sh <http port> --https-port=<n>` from the remembered ports; it is started with `systemd-run` (else `setsid`) so the installer's restart of this service doesn't kill it. Status `running`/`ok`/`failed` in `/tmp/checkin-board.update` (a finished result is only reported for 10 min), output in `.update.log`. In Settings > System the update controls are the last rows of the System card (`#upd-row` Updates/Check, the DreamPi note, `#upd-do-row` Update now, then `#upd-log`); `_log_tail()` returns the last 14 non-empty lines with colour codes, progress-bar rewrites (`\r`) and control characters removed and each line cut at 300 characters, and `renderUpdLog()` shows them as a small scrolling console (`.updlog`, monospace, wraps long lines inside the card, errors red, success green, follows the end while you are not scrolled up). The page polls through the restart and reloads on `ok`. Not verified on a computer: the `systemd-run`/`runuser` path.

**Who runs the update (the web service is not root).** `start_update()` / `start_usb_update()` write nothing and run nothing themselves: they ask systemd to start `checkin-board-update@git.service` (or `@usb`), a root-owned template unit (written by `modules/rebootupdate/install.sh`, with `RuntimeDirectory=checkin-board-update`, which is where progress goes: `/run/checkin-board-update/state.update` and `state.update.log`, written by root, readable by everyone, so the service can not plant anything there). Its `ExecStart` is `modules/rebootupdate/update-run.sh <git|usb>` in the install folder (root-owned, the service can not change it). The script trusts nothing the service can write: the checkout (`src_dir`), its GitHub address (`update_origin`), the branch (`update_branch`), the ports (`install_ports`) and the user (`run_user`) are files in the install folder that only `install.sh` writes; it checks that the checkout's own `origin` is still the recorded address and a GitHub address, runs git as the checkout's owner with `GIT_ALLOW_PROTOCOL=https:ssh`, fast-forwards only, then runs the checkout's `install.sh` with the recorded ports. Because the page can not write the status file before the unit has started, `update_state()` says `running` for up to 30 s after the request until the unit writes its own first line. Tests: `tests/test_update.py`, `tests/test_security.py` (`UpdateOriginTests` runs the real script against a local origin with a stub installer), `tests/test_runuser.py`. **Not verified on a real machine with systemd and polkit** (see `docs/hardware-status.md`).

## Security (`base_security.py`)

The web service runs as an ordinary user (`checkin`, project.json `run_user`), not as root; see "Who runs it" below. Checks done in `base/base_web.py` before an action: `security.host_allowed()` on every request (Host must be an IP, `localhost`, a single-label or private-suffix name, the computer's own host name, or a line in `allowed_hosts` (`core.ALLOWED_HOSTS`); a missing Host header from an HTTP/1.0 client passes; otherwise 421) against DNS rebinding; `security.post_allowed()` on every POST (`Origin`, else `Referer`, must name the request's own Host; the page's `X-Requested-With` header passes; with neither header nor Origin, or with a strict action, 403; only a same-site form post without the header is accepted, and never for the paths a module lists as `PROTECTED`: `/reboot` and `/update/start` from the Reboot and Update module, `/contacts/import` and `/contacts/active` from the Contacts module); for those, `security.check_pin()` with the `X-Pin` header when `core.ADMIN_PIN` exists (PBKDF2-SHA256 salted hash, mode 600, written only by `install.sh --pin` via `base/base_security.py set`, 401 wrong/missing, 429 for 60 s after 5 wrong tries, a damaged file refuses everything). `GET /api` has `pin` (the page prompts once and keeps the PIN in memory only); Settings > About shows a PIN row. Responses carry `X-Frame-Options: DENY`, CSP `frame-ancestors 'none'; object-src 'none'; base-uri 'none'; form-action 'self'`, `nosniff`, `Referrer-Policy: same-origin`. `_body(limit)` clamps Content-Length (a negative one used to read until the timeout); **Settings lock:** Settings > Appearance can set, change and remove the PIN (`POST /pin`, the old PIN is asked for first; while none is set anybody on the network can set one, which is why `install.sh --no-pin` stays) and **Ask for the PIN to open Settings** (`POST /settings-pin`, `core.SETTINGS_PIN`): then the cogwheel asks for the PIN, and every POST that is not a module's `OPEN` path (a dashboard action) needs it too. **PIN pad:** the page asks for a PIN (before an update / reboot, to open a locked Settings, when setting a new one) in its own dialog (`askPin()` in `base/page/page.js`): round number keys 0-9 (also shown when **Ask for the PIN to open Settings** is switched on and no PIN is set yet: the switch asks for a new PIN twice first, `ensure_pin` on the toggle, then locks), a field that also takes a keyboard (a PIN may hold other characters), OK / Enter, Esc or the cross to cancel; checked in `tests/ui/screen.js`. **Screen layout:** `GET`/`POST /screen`, `/screen/stretch`, `/screen/scale`, `/screen/fit`, `/screen/drag`, `/screen/noscroll`, `/screen/autohide` (and `theme` through `POST /screen` {"values": {"theme": "dark"|"light"|"auto"}}) (`core.screen_settings()`, `screen.json`): max columns for the dashboard and Settings, stretch, scale, rearrange, no scrolling; `POST /modules/dashboard-order` reorders the modules after a tile was dragged, and `POST /modules/dashboard-layout` {"cols": n, "columns": [[tile ids] per column]} keeps where every tile is, per number of columns (`core.tile_layout()`, `tile_layout.json`, in `/api` as `tile_layout`): a tile keeps its column and its place in it; one that is not named goes to the shortest column; another screen with the same number of columns shows the same places. **Update:** `origin_problem()` requires the checkout's `remote.origin.url` to match `ORIGIN_RE` (GitHub https/ssh) and equal `update_origin` (written by `install.sh` from the checkout; absent on older installs = accepted once, then recorded); the script fetches that exact URL (`U`) with `GIT_ALLOW_PROTOCOL=https:ssh` instead of the name `origin`, the branch may not start with `-` or contain `..`, the start is under a lock, and the status file/log are removed and recreated with `set -C`/`O_NOFOLLOW` so a planted symlink in `/tmp` isn't followed. `install.sh` writes the unit with `NoNewPrivileges=yes`, `ProtectSystem=full`, `ProtectControlGroups=yes`, `ProtectKernelModules=yes`, keeps `/opt/checkin-board` at mode 755. Tests: `tests/test_security.py`. **Not verified on a computer:** the systemd sandbox directives (a unit that no longer starts would show in `journalctl -u checkin-board`), `--pin` prompting on a real terminal, and `systemd-run`/`runuser` with the pinned-URL fetch. Known gap: the other state files in `/tmp` still have predictable names.

## Who runs it: the user, the folders, the unit (`install.sh`)

- **Folders** (`project.json`: `install_dir`, `data_dir`, `tmp_prefix`, `run_user`; `core.INSTALL_DIR`, `core.BASE_DIR`, `core.TMP_PREFIX`): `/opt/checkin-board` holds the code and what only the installer writes (root-owned, `chmod go-w`; the service reads it): `base_*.py`, `modules/`, `page/`, `project.json`, `admin_pin` (mode 640, group of the service: the service can check the PIN but not change it), `version`, `version_commit`, `src_dir`, `update_origin`, `update_branch`, `install_ports`, `run_user`, `user_created`, `sleep_masked`, `usb_src`. `/var/lib/checkin-board` is the service's (mode 750, owned by it): the roster, the board, settings, photos, sounds, `https.crt` / `https.key`, `settings_pin`, `allowed_hosts`. `/run/checkin-board` (`RuntimeDirectory=`) holds the service's short-lived files (debug log, pokes). A module defines its path constants from `core.BASE_DIR` (state it writes) or `core.INSTALL_DIR` (what the installer writes), never both for one file; `tests/support.py` `sandbox()` redirects both and the run folders.
- **The user:** `install.sh` makes `checkin` (`useradd --system`, no home, `nologin`) when it is missing, remembers it in `run_user` (an update keeps it; `--user=NAME` names another, never root; `uninstall.sh` removes only a user the installer made, noted in `user_created`) and moves the state of an install from before this change out of `/opt/checkin-board` (nothing is overwritten).
- **The unit:** `User=`/`Group=`, `AmbientCapabilities=CAP_NET_BIND_SERVICE` with the same `CapabilityBoundingSet=` (ports 80 / 443), `NoNewPrivileges=yes`, `ProtectSystem=strict` with `ReadWritePaths=<data folder>`, `ProtectHome=yes`, `PrivateTmp=yes`, `PrivateDevices=yes`, `ProtectKernelTunables/Modules/ControlGroups=yes`, `RestrictSUIDSGID=yes`, `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_NETLINK`, `LockPersonality=yes`, `UMask=0027`, `PYTHONDONTWRITEBYTECODE=1` (the installer compiles the code instead). `Nice=-5` is gone (it needs a capability the service does not have).
- **What the service may ask systemd for:** one polkit rule (`/etc/polkit-1/rules.d/50-checkin-board.rules`, JavaScript rules need polkit 0.106+; the installer prints a warning and installs none when `pkaction --version` is older or missing) that returns YES for `org.freedesktop.systemd1.manage-units` with verb `start` and the unit `checkin-board-update@git.service`, `checkin-board-update@usb.service` or `checkin-board-reboot.service`, for the service's user only. The units are root-owned files; the service can start them, not stop, restart or change any unit. `tests/test_runuser.py` pins these names and the installer's settings.
- **Still root:** `install.sh` / `uninstall.sh` / the updater (by hand or through the units above), the PXE network boot server (`pxe/`, it needs the DHCP and TFTP ports and `/var/tmp` image builds; it is opt-in and not part of the web service).
- Checked off hardware: the whole service started as an unprivileged user with the root-owned code folder and the user-owned state folder (reads the PIN hash, imports a CSV, serves HTTP and HTTPS, cannot write the code folder); `install.sh` and `uninstall.sh` run against a stub `systemctl` in a container. **Not** checked: the unit's sandbox directives, the polkit rule and the update / reboot units on a machine with real systemd.

## Service robustness, HTTPS

- HTTPS: `install.sh` makes a self-signed certificate (`https.crt`/`https.key` in `/var/lib/checkin-board`, the key readable by the service only, SAN `<hostname>.local`, the computer's IPv4 addresses; 820 days because Apple rejects > 825; renewed by the installer when < 30 days are left) with `openssl req -config` (no `-addext`, for older OpenSSL). The web service is started as `base/base_web.py <http port> <https port>` (443 by default, `0` = off, `--https-port=N` / `--no-https`). The HTTPS server runs in a second thread; the TLS handshake happens in each request's thread (`finish_request`), so a browser sitting on the certificate warning can't block the accept loop. If the certificate is missing or the port is taken, HTTP keeps working. Both servers are threading (`ThreadingMixIn`).
- **The host never sleeps** (`install.sh`, undone by `uninstall.sh`): `sleep` / `suspend` / `hibernate` / `hybrid-sleep` targets masked (those masked by the installer are listed in `sleep_masked`), `/etc/systemd/logind.conf.d/90-checkin-no-sleep.conf` (idle, lid, suspend / hibernate / power keys ignored); `--allow-sleep` skips it. A suspended host answers nobody until somebody uses it (screens lost contact, ping dead). The network watch also logs when the wall clock jumped ahead of the monotonic one (`ASLEEP`). Run against a stub `systemctl` in `tests/test_nosleep.py`; not verified on hardware.
- **Language** (Settings > Appearance > Language, `POST /language {"values": {"language": "sv" | "en"}}`, the file `language`; `core.language()`: the choice, else `"language"` in `project.json` (a new install is Swedish), else English): one language for the whole host, every screen follows within a second (`/api` carries `lang`; a page that sees another one than it was built with loads again). English is the text written in the code; Swedish comes from **`lang_sv.json`** files: `base/lang_sv.json` (the framework: Settings, colours, PIN, time zones, keyboards, the status menu) and `modules/<name>/lang_sv.json` (a module's own texts; also those of a module that is switched off, its row is in the Modules menu). Format: `{"strings": {"English text": "Svensk text"}, "patterns": [[regex, template]]}`; a pattern is for a text with a number or a name in it: `$1` is the first captured part (translated too: a name stays as it is), `{1?person:personer}` picks by the captured number (singular when it is 1); a module's patterns come before the base's, the general `^(.+): (.+)$` last. The dictionary is built into the page (`window.I18N`, `base_web._i18n_script()`), the page's `tr(text)` (page.js) gives the Swedish text; it passes `setText`, `setLines`, `h()` (text, title, aria-label, placeholder), every `setAttribute` of those, `setHtml` and the pop-up templates (`trDom()`), the layout (`trTree()` at start), a form's options and texts (`take()`), `alert()` / `confirm()`. A text with no entry stays English (and is noted in `TRMISS` in the browser, for the checks). **Adding a text:** write it in English in the code or `layout.json`, add the Swedish one to the module's (or the base's) `lang_sv.json`; `tests/test_i18n.py` fails when a text of a `layout.json` or `module.json` has none. Dates are Swedish throughout (`åååå-mm-dd`, 24 h `tt:mm`, `24/12`, Swedish month and day names, Monday first), in both languages. The text of the board's own buttons (INNE / UTE) and the default statuses (Kommer sent ...) is Swedish in both languages.
- **Network watch** (`base/base_netwatch.py`, a thread of the web service): logs a line (`network: ...`, `journalctl -u <service>`) when an interface's link goes up or down, an address is added, lost or changed, the default gateway changes, or the router stops / starts answering ping; it changes nothing. `diagnose-network.sh` (copied to the data folder by `install.sh`) prints the whole network picture for the host or a screen, read-only.
- **Open pages follow updates** (`PAGE_CODE_VERSION` in `base_web.py`): the page carries a short tag of its program text (`window.PAGE_V`, from page.js, widgets.js, the modules' scripts and boot.js; not the layout or the colours) and every `/api` answer carries the host's (`page_v`); a page that sees another one for more than 3 s loads again, so screens never keep running old code after an update (a page from before this was added has to be reloaded by hand once). An old page's translated values (`av` / `på` for off / on) are still understood by the server.
- **The page's polling** (`refresh()` in `base/page/page.js`): one `/api` question at a time with an 8 s limit (a hung one is given up after 5 s instead of piling new ones up behind it); when the host answers again after contact was lost for 10 s or more, the page reloads itself (clean state, current page files, also after an update of the host). Checked with `tests/ui/outage.js`.
- Web service robustness: listens dual-stack (`::` with IPV6_V6ONLY off, falls back to IPv4) because phones often try the IPv6 address of the .local name first; `request_queue_size` 64; `Handler.timeout` 20 s; every request runs through `_safely()` (500 + traceback in the journal instead of a dropped connection); `watchdog()` GETs `/ping` every 20 s (`ping_ok()`: any `HTTP/1.x 200` counts; it once wanted `HTTP/1.0` while the handler answers `HTTP/1.1`, so the service restarted itself every 90 s and the screens on the LAN lost contact) and exits after 3 failures so systemd restarts it (`Restart=always`, `RestartSec=3`, `StartLimitIntervalSec=0`). The page and static files are kept in memory with their gzip; the page's own POSTs send `X-Requested-With` and get 204 instead of a 303 + full page.

## Measurements

The rows of Settings > System > Info come from the system module (`system_web.about()`: add-on version from `/opt/checkin-board/version` (written by the installer), address, the computer's model and the OS) plus the `about_rows()` of any other module (`modules.collect("about_rows")`). Nothing runs in the background.

## Text, sounds, theme by time of day (screen settings)
- `screen.json` (and a screen's own copy, see Per-screen settings) also holds `font_scale` (0.5 to 2: the dashboard's text size, `--fz`; Appearance > Text size has presets and a slider), `font_colour` (`auto` (default: black on light boxes, the original greys / white on dark ones), `black`, `white` or a palette id; `--rp-text`), `sound` (button sounds on / off), `sound_name` (a file of the sounds folder), `sound_volume` (0 to 1). **Stretch, Scale content and Fit to screen never scale the text:** they grow the rows and the spacing (`--z`), the text has its own scaler. The distance between columns and between the boxes of a column is one token, `--gap` (12 px).
- **Button sounds:** `/var/lib/checkin-board/sounds/` (`core.SOUNDS_DIR`; the add-on's `pop.wav`, `tick.wav`, `bubble.wav` are copied there by `install.sh`; copy any `.wav`, `.mp3` or `.ogg` of at most 2 MB in by hand and it appears in Appearance > Button sound). `GET /sounds/<name>` serves a listed file only. The page decodes it (an offline audio context, so no sound is needed to start) and plays it with the Web Audio API on every button press (`pointerdown`).
- **Theme "By the time of day"** (`theme: "time"`): light while the sun is up, dark at night, for a computer whose system has no light / dark setting. `/api` has `daylight: {elev, day, zone}` (`core.daylight()`: the sun's height in degrees at the place of the common time zone, or the computer's own: the first city of `base_tz.CITIES` with that zone, else the middle of the zone's offset band at 50 degrees north; `base_tz.sun_elevation()`); the page switches `data-theme` from it. The Snow background module draws its day and night from the same number.
- `GET /screen` (the form) lists `sounds` (with **Off** first: `sound_name: "off"` switches the button sounds off, a file name switches them on with that file), `sizes` and `font_colours` as options.

## Backup (system module, Settings > System)

`GET /backup` downloads a zip (`system_web.make_backup()`) of the data files in the data folder: every `<name>.json` (the roster, the board, the modules switched on, the palette, the screen settings ...), `time_zone`, `language`, `background_image`, `photos/` and `screens/<id>/*.json`, plus `backup.info` (date and add-on version). Not in it: the PINs, the HTTPS key and certificate, `allowed_hosts`, the update origin, `project.json` and the layout / language files (program files). `POST /backup/restore` (PIN-protected) takes `{"backup": <base64 of the zip>}`; `restore_backup()` accepts only names that `_member_ok()` allows (no paths outside the folder, no program files, JSON files must parse) and checks the whole zip before it touches anything; then the backup's state replaces the current one (files the backup lacks are removed), and the page reloads. Tests: `tests/test_backup.py`. Not tried with a real computer; the other screens follow on their next poll.

## Settings address and the cogwheel

`GET /settings` serves the same page as `/`; the page (`settingsRoute()` / `openSettingsRoute()` in `page.js`) opens Settings by itself, **asks for the PIN first whenever one is set** (the PIN pad, checked with `POST /pin/check`; a wrong PIN asks again, cancelling goes back to `/`) and closing Settings goes back to `/`. **Appearance > Layout > Hide the top bar completely** (`nobar`, `POST /screen/nobar`: the whole bar is gone, building buttons and cogwheel too, not even at the edge) and **Hide the cogwheel** (`nocog` / `nobar` in `screen.json`, `POST /screen/nocog`, per screen like the other layout settings) takes the cogwheel out of the top bar, so a wall screen can not open Settings by a tap; it is reached at `<address>/settings`. Browser check: `tests/ui/menus.js`. The PIN only gates what it gates elsewhere too: the board stays readable, and with no PIN set `/settings` opens for anybody on the network.
