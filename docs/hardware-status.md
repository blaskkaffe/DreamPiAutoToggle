# What is verified on real hardware

Check this before saying something works. Anything not listed under Verified has only been tried in simulation or unit tests. Update it whenever the user reports a hardware result. Back to [CLAUDE.md](../CLAUDE.md).

## Verified on hardware

- The hook loads and patches under DreamPi's real Python 2.7.
- A real DCNet call end to end via the DCNet number (`333-3333` at the time, now `555-0002`); the routing logic (`_special()`/`endswith()` matching, `dcnet_mode`, `dcnet_connect()`) is unchanged by the renumbering, only the literal digits matched.
- A single NeoPixel on GPIO18 (PWM FIFO path, `FifoPixel`).
- The modem status/port pipeline: on a real CDC-ACM modem (`/dev/ttyACM0`), DreamPi's own `Opening serial interface to ...` log line was correctly matched and shown as "Opening modem on /dev/ttyACM0", confirming `_MODEM_EVENTS` and `_write_port()` work on hardware the earlier simulation-only testing didn't cover. (This was also how the removed AT-probe's problem was found: it stopped DreamPi right after this message, and DreamPi got stuck re-opening the port on restart - see the modem identification note above.)

## Not yet verified

- The strip path (`DmaStrip`, PWM + DMA, `--leds=N` with N > 1); only tested against fake memory and mailbox.
- Whether port 80 is free on every DreamPi image.
- LED temporal dithering, wire order, gamma and white balance: the quantization/dithering math and the byte-order permutation are covered by plain Python tests (no hardware needed for those), and the gamma/white-balance pipeline itself is simple enough to verify the same way (full-on unaffected, a mid value compressed by gamma, black staying black regardless of white balance, a channel multiplier scaling only that channel - all confirmed with `to_bytes()` called directly), but whether breathe genuinely looks smoother, and whether the white-balance sliders against a real LED actually produce a neutral white, haven't been checked against a real strip. This pipeline replaces an earlier 9x3 hue/lightness swatch-calibration grid (`calib_table()`/`calib_offset()`/`_row_interp()`/`_hue_interp()`, removed) - see git history before reviving anything like it. That grid had already needed one real-hardware bug fix of its own (a dark-pixel tinting bug, since moot) when the user asked for it to be replaced outright with something simpler: a flat per-channel white-balance multiplier plus a standard gamma curve, calibrated by eye against solid white in about 30-60 seconds instead of matching dozens of individual swatches.
- The installer's changes to the button service (always installed; `--wifi` only the Wi-Fi half; migration of an older `dreampi-netswitch-wifi` install) were checked for shell syntax and option parsing only, not run on a Pi.
- Changing the LED count or output pin from the page at runtime (closing and reopening the hardware output without restarting the service).
- GPIO12, GPIO21 (`PcmStrip`) and GPIO10 (`SpiStrip`) entirely: GPIO18 is the only pin ever tried on real hardware. The PCM register values are cross-checked against rpi_ws281x's source, not a datasheet or a real PCM peripheral; the SPI approach is this add-on's own former default for GPIO10 (verified back then), generalised here to any LED count/order/calibration rather than re-tested as-is.
- Modem identification: the USB descriptor lookup (`_usb_info()`) is plain sysfs reads and should be safe, but is itself only tested in simulation, not against a real modem's actual sysfs layout (e.g. a CDC-ACM modem at `/dev/ttyACM0`). `KNOWN_MODEMS`/`UNKNOWN_MODEMS` come from a DreamPi forum thread the user pasted in, not first-hand testing here.
- Whether the Dreamcast reacts as expected to the busy tone from a hang-up number (Reset / Toggle, e.g. `5550001#`).
- Configurable phone numbers (`numbers.json`, endings, `*61#`-style entries, longest match): the matching and the `check_number()` wrapper are tested against a fake `Netlink`; whether DreamPi really delivers `*` and `#` in the dialed string the way the tests assume (it did for the old `#` suffix numbers' format, which itself is unverified on hardware) has not been checked on a Pi.
- Everything in [Buttons and Wi-Fi setup](buttons-wifi.md): the button GPIO reading, `hostapd`/`dnsmasq` AP hosting, `wpa_supplicant.conf` writing and reconnecting, and the assumption that DreamPi's OS image uses `wpa_supplicant`/`dhcpcd` rather than NetworkManager. Only unit-tested off-hardware (scan-result parsing, `wpa_supplicant.conf` dedup/rewrite, LED default-effect selection, page rendering, and the button debounce/hold/combined-hold dispatch logic, see Testing above) - see the git history for what was checked and how before treating this as working. The (single) button itself already had one real bug found on hardware (the classic-Pi pull-up/down register mixup, see `set_input_pullup()` in `netswitch_gpio.py`), now fixed but not yet reconfirmed on the Pi 3 that found it. The later generalisation to two independently-configured buttons, per-button functions, the `"12"` combined-hold assignment, and the GPIO settings box's live config-reload in `netswitch_buttons.main()` are new on top of that and have not been tried against real buttons at all.
- The LED service now always installed (default 1 LED, `--leds=N`, `--leds=0` idling it and hiding the LED settings) and the `switch_output()` open/close logic: unit-tested with a fake driver, installer option parsing tested in a stub shell, not run on a Pi.
- Button startup: the first press right after an install was reported not to register (later presses were fine). Cause not found. `button_watcher()` now waits for the pull-up to settle, seeds each button from its real level (a pin already low at start can't fire a function on release) and re-applies the pull-up every second while a pin sits low; with the debug log on (`debug_dtmf`) it logs the idle levels at start and every short press (`button: watching GPIO17+4, idle level high/high`). Unconfirmed on hardware.
- Update check and Update now: the GitHub comparison is tested against fake responses and the update script against a local git origin with a stub installer (fast-forward, refused when diverged); the real GitHub API calls were not exercised from the test sandbox beyond fetching the repo head, and the `systemd-run` + `runuser` launch has not run on a Pi.
- Wi-Fi demo mode (`--wifi-demo`): the cycle, states and page list/connect/fail flow driven end to end in a browser against dummy networks (no Pi). Real Wi-Fi hardware paths remain unverified.
- Toggle-switch button functions (`sw_dcnet`, `sw_dcnow`, `sw_wifi`, `sw_wifi_off`): logic tested with scripted pin levels and a fake clock (`LoopTests`), page checked in a rendered screenshot; no real switch has been wired up, and Wi-Fi setup itself is unverified (see above).
