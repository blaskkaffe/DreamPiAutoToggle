# What is verified on real hardware

Check this before saying something works. Anything not listed under Verified has only been tried in simulation or unit tests. Update it whenever the user reports a hardware result. Back to [CLAUDE.md](../CLAUDE.md).

## Verified on hardware

- The hook loads and patches under DreamPi's real Python 2.7.
- A real DCNet call end to end via the DCNet number (`333-3333` at the time, now `555-0002`); the routing logic (`_special()`/`endswith()` matching, `dcnet_mode`, `dcnet_connect()`) is unchanged by the renumbering, only the literal digits matched.
- A single NeoPixel on GPIO18 (PWM FIFO path, `FifoPixel`).
- The modem status/port pipeline: on a real CDC-ACM modem (`/dev/ttyACM0`), DreamPi's own `Opening serial interface to ...` log line was correctly matched and shown as "Opening modem on /dev/ttyACM0", confirming `_MODEM_EVENTS` and `_write_port()` work on hardware the earlier simulation-only testing didn't cover. (This was also how the removed AT-probe's problem was found: it stopped DreamPi right after this message, and DreamPi got stuck re-opening the port on restart - see the modem identification note above.)

## Not yet verified

- Button sounds (from the `checkin2.0` branch): the sound files, the `/sounds/` route, the settings and the form are tested off-hardware; the playback in a real browser on the user's device has not been tried here.

- The settings cache (`core.cached()`): measured on a PC only (an `/api` answer 13 ms -> 3 ms, a page load and a POST similar); the Pi's own speed after it has not been measured. The lag the user saw on the Pi after the base split was the repeated palette / module lookups; whether it is gone on the Pi is for the user to say.

- The base / project split, steps 3 to 5 (every module owns its state files and readers, `base/layout.json` is copied by `install.sh` and draws the base's Settings boxes, the checker's `net` file carries `dcnet_problem` / `dcnet_code` for the LED and openMenu modules, `/tag` is served by the switcher module): tested off-hardware only (617 tests, the browser audit against the demo server). Not run on a Pi: an upgrade of an existing install through the new installer, the LED service reading DCNET availability from the `net` file instead of the config files, and openMenu's DCNET line from the same file.

- The base split, step 2 (the hook moved to `modules/switcher/netswitch_dreampi.py`, the `.pth` now names `/opt/dreampi-netswitch/modules/switcher` and is written by `modules/switcher/install.sh`; the buttons service `dreampi-netswitch-buttons` is installed by the same script; the numbers matching is `modules/numbers/netswitch_numbers_hook.py`): tested off-hardware only (hook against a fake Netlink, installer shell syntax, layering tests). Not run on a Pi: the installer upgrading an existing install (the old `.pth` is rewritten, the old `netswitch_hook.py` / `netswitch_probes.py` / `netswitch_buttons.py` are removed) and DreamPi's Python 2.7 loading the hook from the new folder - the earlier "hook loads and patches under Python 2.7" result was for the old location.

- The layout-driven page (every box is a module's `layout.json` drawn by the standard widgets in `page/widgets.js`; module picker with drag-and-drop order and priority (mouse drag and keyboard tested in Chromium; touch dragging is tested with touch events in a phone-sized Chromium context, but **not on a real iPhone/Safari** (the user found the first version buggy there; the likely cause, the grabbed row being re-inserted into the page during the drag, is fixed and has a regression test, but whether iOS Safari is now smooth is unconfirmed)); 16-colour palette, per-module primary colour that follows the selected network; fullscreen / part backgrounds): tested off-hardware in Chromium against the demo server (`sh tests/ui/run.sh`: layout at four widths, `tests/ui/functional.js` drives network switching, colour pick, numbers table, forms, module move / switch, debug log) and by unit tests; **not seen on a real phone, on real Pi hardware or with a real DreamPi** (every state the widgets show is simulated: the switcher's status rows come from the real code paths but the demo has no DreamPi, modem or Wi-Fi). A part-type background has no module yet, so that path is tested at the loader only.
- The module system (`modules/<name>/`, Settings > System > Modules, `base_modules.py`): tested off-hardware - every module deleted alone and switched off alone while the web service runs, the base alone (browser run against the demo server with `OFF=all`, no JS errors), a broken and a new module, the LED service driving 0 LEDs while its module is off, the hook with the debug log and numbers modules present / absent / off, and `install.sh`'s `sync_modules` on temp folders. **Not run on a Pi:** the installer's service handling (the LED unit written by `modules/led/install.sh`, the Wi-Fi unit written by `modules/wifi/install.sh` (Wi-Fi setup now runs in its own `dreampi-netswitch-wifi` service, not in the buttons service; its start/stop/module-off handling is unit-tested with a fake setup cycle only), replacing the old combined `dreampi-netswitch-wifi` unit, removing it when the module is gone, `ConditionPathExists=` skipping it when its files are deleted from `/opt/dreampi-netswitch`), `modules/wifi/install.sh` (`--wifi`, converting the old `wifi_enabled` marker), and an update from the old flat layout (the old copies are deleted by `install.sh`).

- LED engine rebuild (solid / blink, hue-preserving `quantize()`, 0.4 s `Steady` debounce, 3 s keepalive, best-effort `SCHED_FIFO`, atomic hook state files, global network colours): tested off-hardware (`tests/test_led_engine.py`: a dimmed #ff8c00 never turns green or non-monotonic down to 0.1 %, the colour mix survives dimming for eight colours, blink timing; `tests/test_network_colours.py`). Whether the flicker the user saw on the Pi is gone, and whether `SCHED_FIFO` is allowed and helps, is **not verified on a Pi**. The red and green network colours are approximations of the Dreamcast BIOS buttons (exact values unknown), and how all four look on the real LED after gamma has not been seen.

- LED colour groups (rows of colour, animation and level, each with the messages that light it; defaults; priorities; targeting of one LED / ranges; the old per-message `led.json` giving the default rows) and the "off" fallback: tested off-hardware (`tests/test_led_messages.py`; the page driven in a browser). Not seen on a real LED: how the colours look after gamma on the actual NeoPixels. The new signals behind the messages are only simulated, **never run on a Pi**: the ping probe (slow connection), Wi-Fi signal from /proc/net/wireless, no-IP detection, DNS failing, under-voltage/throttled/temperature flags, the update-available file and the reboot marker. *Your game is played* and *A friend came online* are configurable but never light (nothing detects them). Updates are only checked when the user presses Check now (no background check).

- Web-service safety (Host/Origin checks, optional PIN, update origin pinning, systemd sandbox directives on `dreampi-netswitch.service`, `wpa_supplicant.conf` mode 600): tested off-hardware (`tests/test_security.py`, PIN prompt flow driven in a browser against the demo server). Not run on a Pi: whether the sandboxed unit starts and still restarts DreamPi / reboots / starts the update on every Raspberry Pi OS version, and `install.sh --pin` on a real terminal. See [web.md](web.md#security-base_securitypy).

- The strip path (`DmaStrip`, PWM + DMA, `--leds=N` with N > 1); only tested against fake memory and mailbox.
- Whether port 80 is free on every DreamPi image.
- LED wire order, gamma and white balance: the quantization math and the byte-order permutation are covered by plain Python tests (no hardware needed for those), and the gamma/white-balance pipeline itself is simple enough to verify the same way (full-on unaffected, a mid value compressed by gamma, black staying black regardless of white balance, a channel multiplier scaling only that channel - all confirmed with `to_bytes()` called directly), but whether the white-balance sliders against a real LED actually produce a neutral white, haven't been checked against a real strip. This pipeline replaces an earlier 9x3 hue/lightness swatch-calibration grid (`calib_table()`/`calib_offset()`/`_row_interp()`/`_hue_interp()`, removed) - see git history before reviving anything like it. That grid had already needed one real-hardware bug fix of its own (a dark-pixel tinting bug, since moot) when the user asked for it to be replaced outright with something simpler: a flat per-channel white-balance multiplier plus a standard gamma curve, calibrated by eye against solid white in about 30-60 seconds instead of matching dozens of individual swatches.
- The installer's changes to the button service (always installed, no Wi-Fi code in it; the Wi-Fi half is the module's own service; migration of an older `dreampi-netswitch-wifi` install) were checked for shell syntax and option parsing only, not run on a Pi.
- Changing the LED count or output pin from the page at runtime (closing and reopening the hardware output without restarting the service).
- Switching SPI on and off by itself for GPIO10 (`netswitch_led_spi.py`: the config.txt edit is unit-tested on a temp file, but neither `dtparam spi=on` taking effect without a reboot nor the line removal has been tried on a Pi).
- GPIO12, GPIO21 (`PcmStrip`) and GPIO10 (`SpiStrip`) entirely: GPIO18 is the only pin ever tried on real hardware. The PCM register values are cross-checked against rpi_ws281x's source, not a datasheet or a real PCM peripheral; the SPI approach is this add-on's own former default for GPIO10 (verified back then), generalised here to any LED count/order/calibration rather than re-tested as-is.
- Modem identification: the USB descriptor lookup (`_usb_info()`) is plain sysfs reads. **Seen on a real Pi:** it read the user's modem as "Conexant USB Modem", which the user reports works well with DreamPi, so that name is now in `KNOWN_MODEMS`. Other modems' sysfs layouts (e.g. a CDC-ACM modem at `/dev/ttyACM0`) are only tested in simulation, and the rest of `KNOWN_MODEMS`/`UNKNOWN_MODEMS` comes from a DreamPi forum thread the user pasted in, not first-hand testing here.
- Whether the Dreamcast reacts as expected to the busy tone from a hang-up number (a row with *Hang up after the action*, e.g. DCNow! with `5550001#`; there is no such row by default, add one first).
- Configurable phone number rows (`numbers.json`, actions announced by modules and done by their hook files, several rows per number, the default `11111` row catching openMenu's `1111111`, endings, `*61#`-style entries, longest match): the matching and the `check_number()` wrapper are tested against a fake `Netlink`; whether DreamPi really delivers `*` and `#` in the dialed string the way the tests assume (it did for the old `#` suffix numbers' format, which itself is unverified on hardware) has not been checked on a Pi.
- The LED colour rows as a priority list (the order of the rows decides, messages announced by the modules, the migration of an older `led.json` with a separate message priority): tested off-hardware only (the engine itself is as before).
- LED latency: **seen on a real Pi** (user report): a change took over 2 s while a changed frame was sent once and then only every 3 s; after the frame was sent 6 times in a row and then every 0.5 s (`BURST`, `KEEPALIVE`) it is fast again, so the likely cause was a frame that did not take on the LED. Not measured in milliseconds on the Pi. The loop itself reacts within about 40 ms with a simulated output (`tests/test_led_loop.py`). The debug log (Recording) and `journalctl -u dreampi-netswitch-led` say where the time goes if it comes back.
- Everything in [Buttons and Wi-Fi setup](buttons-wifi.md): the button GPIO reading, `hostapd`/`dnsmasq` AP hosting, `wpa_supplicant.conf` writing and reconnecting, and the assumption that DreamPi's OS image uses `wpa_supplicant`/`dhcpcd` rather than NetworkManager. Only unit-tested off-hardware (scan-result parsing, `wpa_supplicant.conf` dedup/rewrite, LED default-effect selection, page rendering, and the button debounce/hold/combined-hold dispatch logic, see Testing above) - see the git history for what was checked and how before treating this as working. The (single) button itself already had one real bug found on hardware (the classic-Pi pull-up/down register mixup, see `set_input_pullup()` in `base_gpio.py`), now fixed but not yet reconfirmed on the Pi 3 that found it. The later generalisation to two independently-configured buttons, per-button functions, the `"12"` combined-hold assignment, and the GPIO settings box's live config-reload in `netswitch_buttons.main()` are new on top of that and have not been tried against real buttons at all.
- The LED service now always installed (default 1 LED, `--leds=N`, `--leds=0` idling it and hiding the LED settings) and the `switch_output()` open/close logic: unit-tested with a fake driver, installer option parsing tested in a stub shell, not run on a Pi.
- Button startup: the first press right after an install was reported not to register (later presses were fine). Cause not found. `button_watcher()` now waits for the pull-up to settle, seeds each button from its real level (a pin already low at start can't fire a function on release) and re-applies the pull-up every second while a pin sits low; with the debug log on (`debug_dtmf`) it logs the idle levels at start and every short press (`button: watching GPIO17+4, idle level high/high`). Unconfirmed on hardware.
- `GET /tag` for openMenu and the Reboot button: the endpoint/server side is tested (`tests/test_tag_reboot.py`); nothing has requested `/tag` from a real Dreamcast/openMenu, and the reboot has not been run on a Pi (it uses `systemctl reboot` after a 2 s delay).
- Online players list: the two default feeds (dc99.net status page, dreamcast.online users.json) and their field names come from openMenu's working code; the parser, cache and page are tested with responses built to those shapes. This add-on has not seen a real response (both hosts are blocked from the development sandbox). An earlier version showed only DCNET players on the Pi although openMenu showed DCNow! and KOSnet too; the cause was not seen, the parser was made generic (any section with a players/users list, KOSnet included), dreamcast.online was added as a second source and the page shows per-source section counts so a missing network can be diagnosed. Still to be confirmed on a Pi.
- Update check and Update now: the GitHub comparison is tested against fake responses and the update script against a local git origin with a stub installer (fast-forward, refused when diverged); the real GitHub API calls were not exercised from the test sandbox beyond fetching the repo head, and the `systemd-run` + `runuser` launch has not run on a Pi.
- Wi-Fi demo mode (`--wifi-demo`): the cycle, states and page list/connect/fail flow driven end to end in a browser against dummy networks (no Pi). Real Wi-Fi hardware paths remain unverified.
- Toggle-switch button functions (`sw_dcnet`, `sw_dcnow`, `sw_wifi`, `sw_wifi_off`): logic tested with scripted pin levels and a fake clock (`LoopTests`), page checked in a rendered screenshot; no real switch has been wired up, and Wi-Fi setup itself is unverified (see above).
- DCNow! selected after every reboot (`netswitch_switcher_state.reset_network_after_boot()`, keyed on the kernel's boot id, run when the web service and the buttons service start): unit-tested with a fake boot id, **not verified on a Pi** (a real reboot with DCNET selected has not been tried).
- The Dreamcast background as a module (served from `modules/background/`): loaded in headless Chromium with a software WebGL renderer against the demo server, no page errors; the original per-browser switch is gone. Not looked at on a phone or a real GPU since the move.
- Favorite players and games (players module): the favorites, the game-list parser and the LED messages `players-game` / `players-friend` are tested off-hardware only. The Dreamcast Live game table parser was written from a copy of the table the user pasted (not fetched); which page of dreamcastlive.net holds it is an unverified guess (host blocked from the development sandbox), so the bundled snapshot may be what is shown. The LED lighting on a real strip is not confirmed.

- Clock module (12h / 12h am/pm / 24h time, the large clock, .beat, the common time zone, world times, the city list and the stylised time zone map): tested off-hardware (`tests/test_module_views.py`, `tests/ui/clock.js` in headless Chromium). Summer time comes from `zoneinfo` or, on Python before 3.9, from the add-on's own reader of the system's tz files (`base_tz.py`, checked against `zoneinfo` on the development machine). Not run on a Pi: which of the two its Python uses, how old its tz database is (a very old one may lack a recent rule change; a zone it does not know is left out of the lists), and how the page and the map look on a phone.
- Notification highlight and notices (the rainbow edge / colour glow, a neutral box turning its colour, the banner): seen in headless Chromium at four widths and checked by `tests/ui/events.js`; not looked at on a phone.
- DC99 events module: the data source was found by opening dc99.net/community in a browser (October 2026): the `const EVENTS = [...]` list in the page. The importer, store, API and reminders are tested with pages built the same way and with real events copied from it (`tests/test_events.py`, `modules/events/sample_events.json`, `tests/ui/events.js`); the development sandbox cannot reach dc99.net, so the add-on itself has **not downloaded the real page yet**. The time zone rule (US Eastern, UK for "UK" events) is inferred from DreamcastLive's schedule and DC99's listing; the LED message has not been seen on real LEDs.

- New LED effects (fade, breathe, short / double / triple blink, rainbow), Ready for calls per network, the editable palette with a per-colour LED value and its Preview on LED: the maths and timings are tested off-hardware (`tests/test_led_engine.py`, `tests/test_led_messages.py`) and the page's preview in a browser. **Not seen on a real LED**: how the fades look at a low maximum brightness (few steps, no dithering), whether the lowest breath step is visible and keeps its hue, how the rainbow looks after gamma and white balance, and whether the default colours need changing.
- LED reaction time and the faster checks (`checker_step()` every 0.5 s, the LED service's quick look at the state files, `core.poke("internet")` from the hook): tested off-hardware, with the LED driver simulated (a change shows about 0.2 s after the file is written). Not measured on a Pi: the CPU use of the half-second checks, and whether the shorter hold (0.12 s) lets a flicker through while DreamPi starts or ends a call.
- openMenu link module (`modules/openmenu/`): the Pi side (poll, game upload, the launch handshake, the texts of the box, the `NET` / `DCNET` / `PLY` / `EVENT` lines, which games are announced as online, the poke that makes the players list current) is tested off-hardware (`tests/test_openmenu.py`, `tests/test_players.py`) and the boxes in headless Chromium (`tests/ui/openmenu.js`: the search, Start asking first, the buttons off while disconnected, the Join buttons in the Online players box). **Never run with a Dreamcast or a Pi**; the openMenu side was only syntax-checked by its author and does not read these lines yet. That the `slot` in the upload is the number openMenu wants in `PLY` (slot:players) was taken from the openMenu author's own message, not checked.
