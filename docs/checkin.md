# The check-in board and the contacts

Read before touching `modules/checkin/`, `modules/contacts/`, the `roster` widget (`page/widgets.js`) or the kiosk script. Back to [CLAUDE.md](../CLAUDE.md). The idea and most of the features come from CheckinChicken (a Node.js check-in board); this is the same board as two modules of the add-on's module base.

## How it fits together

- **One host, any number of screens.** The computer that ran `install.sh` is the host: its web service holds the roster and who is in. Every other screen is only a browser that opens the host's address (full screen, in kiosk mode if you like: `kiosk/kiosk-browser.sh <host>`), so they show the same thing. A screen can also be the host itself.
- **In step in real time.** `api()` of the check-in module puts the whole board (`d["checkin"]`: groups, people, the status menu, buildings, a revision) into every `GET /api` answer, which every page asks for once a second, and a tap POSTs and redraws at once from the answer. A change on one screen is on all of them within about a second. The revision (`"<state revision>.<roster stamp>"`) changes with every tap, status, setting and import, so the widget redraws only when something changed. No socket, no server-sent events: nothing to keep alive over a flaky Wi-Fi link. If the polling ever becomes a limit, a long-poll on `/checkin?since=<rev>` is the next step (the revision is there for it).
- **No standalone server needed**, but possible: the web service is plain Python 3 and runs anywhere (`python3 netswitch_web.py 8080 0` after pointing the paths in `netswitch_core.py` somewhere writable; or `python3 tests/ui/demo_server.py` for a sandbox with sample people). Syncing the state between **several hosts** (every screen its own server) is not built: all state is in `checkin.json` / `contacts.json` and every change goes through one lock and one atomic write, which is the shape a later peer-to-peer sync would need.

## Contacts (`modules/contacts/`)

- **Import** (Settings > Contacts): a CSV file or pasted text, `POST /contacts/import {"csv", "replace"}` (PIN-protected when a PIN is set). Columns as in CheckinChicken's `people.csv`: `name, department, role, phone, location, restrictToLocation`. `location` is the **building** (CheckinChicken's "Område" / coop). Lines that start with `#` and blank lines are skipped; comma, semicolon and tab are found from the header line; a BOM is ignored; Swedish headers (`namn`, `avdelning`, `roll`, `telefon`, `omrade`) and `building` are accepted. `restrictToLocation` is `1/true/yes/ja/x`.
- **Merging, never deleting:** a person is found again by building + department + name (`person_id()`, a short hash), updated in place and kept in step with their check-in state; people not in the file stay unless "Switch off people that are not in the file" is ticked (they get `active: false` and leave the board; the data stays). A person with no department gets "No department". At most 2000 people.
- **Files:** `contacts.json` (`core.CONTACTS`: `{"people": [{id, name, department, role, phone, location, restrictToLocation, active, order}]}`), written only by this module. `GET /contacts` (the count text for Settings), `GET /contacts.csv` (export), `python3 modules/contacts/netswitch_contacts.py people.csv [--replace]` imports from a shell.
- The board reads `contacts.json` directly, so it works while the contacts module is off (only the import box and the endpoints are gone).

## Check-in board (`modules/checkin/`)

- **State** `checkin.json` (`core.CHECKIN`): `{"rev", "config": {group_by, colour_by, colours}, "statuses": null | [...], "people": {id: {in, status, detail, at}}}`. Everything goes through `_lock` and an atomic write (`_save()` bumps `rev`).
- **A person's row:** grey while out; the **INNE** (green) / **UTE** (red) button at its right switches in <-> out (the state is on the button) and a tap anywhere else on the row opens the status menu; in = the whole row in the colour of the person's department or building (`colour_by`); a status gives the row the **status' own colour**, and while a status is set the name and the status scroll round like a carousel (`"Erik Lindqvist · Kommer sent · 08:15"`). A status that is `out` (Sjuk ...) also shows UTE. `POST /checkin/toggle {id}` (in <-> out, **keeps the status**), `POST /checkin/status {id, code, detail}` (`code` a status code, `""` = clear; `IN` / `OUT` still work), `POST /checkin/all {in}` (everybody in / out, statuses cleared).
- **Statuses** are CheckinChicken's menu, Swedish labels, with palette colours: FYS, Kommer sent (time), Går tidigare (time), Tjänsteresa (date, "tillbaka"), Sjuk, Jobbar hemifrån, Semester (date), VAB, Läkarbesök (time), Föräldraledig, Personlig dag, Annat (a note). A status that is `out` (Sjuk, Semester ...) also checks the person out; the others keep in / out. INNE / UTE changes in / out without touching the status. The list is `DEFAULT_STATUSES` in `netswitch_checkin.py`, replaced by `checkin.json` `"statuses"` (a list of `{code, label, colour, needs: time|date|note, default, prefix, out}`, at most 16, colours palette ids). A detail is cleaned on the server (a time is `HH:MM`, a date becomes `d/m`, a note at most 60 characters). Not ported from CheckinChicken: the "plupp" dot statuses and the admin editor for the menu.
- **Colours are palette ids only** (`AUTO` cycles through twelve of them by the sorted department / building name; Settings > Check-in board lists every department and building with a select to give it one, `POST /checkin/colour {kind, name, colour}`; "Automatic" goes back). `colour_by` and `group_by` are `department` or `building`, so "department and/or building" is a setting.
- **The look** (the `roster` widget): one box per group (department or building, `group_by`) in a single column; the box's top row names the group and counts who is in (`3/10`); under it a row per person, large text (1.75em), rows full width to the box edge with thin dividers, the name on the left, the status or the role on the right and the small **Status** button inside the row. Sized so that 60 people fit a 1080p screen once the page has columns (checked with temporary CSS: three columns in landscape, two in portrait, about 1010 px of 1080 and 1920 used); the page itself has one column for now, the multi-column support comes from the `development` branch.
- **Status menu:** a pop-up in the middle of the screen, about 60 % of its width (the whole width on a phone), with a dimmed backdrop. At the top the person: **photo** (initials in a coloured circle until there is one; tap it to choose a picture, which the browser cuts to 160 px and the contacts module keeps in `photos/`), name, department and building, role, phone; a cross in the top right corner (a click outside or Esc closes it too). Below, every status as a button of one size, three in a row, in its colour, and **Clear status**; a status that needs a time / date / note first shows the field with the default (`07:30` ...) and a **Set** button.
- **Buildings filter:** with two or more buildings a chip row ("All", one per building) picks what this screen shows; the choice is kept in this browser (`localStorage` `checkin:locations`) and `?location=A,B` in the address sets it (`kiosk-browser.sh <host> "Område A"`). People with `restrictToLocation` show only when their own building is picked, never under "All"; people with no building show everywhere they are not restricted.
- **Settings** also has the colour of the module (Appearance), "All out" / "All in" (tap twice).
- **Photos:** `POST /contacts/photo {id, photo: "data:image/jpeg|png;base64,..."}` (empty = remove; at most 150 KB, checked by its first bytes, stored as `/opt/dreampi-netswitch/photos/<id>.jpg|png`, written by the contacts module), `GET /contacts/photo/<id>` serves it (cached an hour; the board's `photo` url carries a version so a new picture shows at once). The board has the urls, never the pictures, so `/api` stays small. Not PIN-protected (anyone who can open the page can set a photo).
- **Not ported yet** from CheckinChicken: the admin passcode screen (the optional PIN of this add-on guards the import), per-screen titles, the themes, the on-screen keyboard and the admin editor for statuses and people.
