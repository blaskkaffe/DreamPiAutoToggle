# Status LEDs, colours and calibration

**The LED part is a module** (`modules/led/`, see [modules.md](modules.md)): `netswitch_led.py` (the service), `netswitch_led_drivers.py`, `netswitch_ledconfig.py` (settings and messages, shared by the service and the web side), `netswitch_led_web.py` (the page's endpoints: `GET`/`POST /ledrows` (the looks, as the standard `triggers` rows: one per colour group, the order is the priority), `GET`/`POST /ledconfig` (the calibration only: `max_brightness`, `white_balance`, `gamma`; it keeps the rows and the saved wire order), `GET`/`POST /ledhardware` (the LED row of the GPIO box: count, wire order, pin; the standard form answer `{values, options}`), `/wbtest`, `/wbtestdone`, `/ledcolours`, and `api()`: the dot's look and `d["led"]` = `installed` / `count` / `title`), `layout.json` (the form in the `gpio` box and the **Status LED** box, `show`n only while the LED count is above 0, titled `@led.title`: the custom widget `led-tools` (Calibration and Colours rows) and the `triggers` widget over `/ledrows`), `messages.html` + `page.js` (the custom widget `led-tools`: the calibration pop-up with its white-balance preview and the palette editor), `install.sh` / `remove.sh` and `module.json` (with `led_messages`: the general messages `ok`, `error`, `warning`, `off`). Without the module (deleted folder, or switched off in Settings > System > Modules) `/ledrows` and the others answer 404 and the DreamPi dot gets a plain look from the switcher's `_dot_look()`. The service drives 0 LEDs while the module is off (`wanted_count()`). `base_gpio.py` stays in the base: the buttons use it too.

Read before touching anything in `modules/led/`. Back to [CLAUDE.md](../CLAUDE.md).

## Messages, settings file and calibration

- **LED groups and messages** (`netswitch_ledconfig.py`): a *message* is something the add-on can tell. **The modules announce them** in their `module.json` (`"led_messages": [{"id", "label", "group", "description"}]`; the switcher: DreamPi, calls, network selection, connection, modem and Pi health; the Wi-Fi module: Wi-Fi setup; rebootupdate: updates and reboot; players, events; the LED module: Everything OK / Error / Warning / Off), and `core.module_led_messages()` / `ledconfig.messages()` lists those of the **enabled** modules in picker order: they are the triggers a row can pick. A message of a module that is off is not offered and never lights (`active_messages()` drops it), but a row keeps it. How each message is detected is still code: `active_keys(ctx)` below. A *group* is one look: `{"id", "colour", "effect", "speed", "brightness", "leds", "messages": [keys]}`. A group is lit while any of its messages is true, and a message belongs to at most one group (`clean_groups()` keeps the first; any key of the form `a-b` is kept, so a row keeps the messages of a module that is off), so a message in no group never lights. **The order of the groups is the priority**: the top group wins. `colour` is a palette id or a token (`COLOUR_TOKENS`: `dcnow`, `dcnet` = the switcher module's network colours; `network` is the palette entry that follows the *selected* network); `resolve_colour()` turns it into the LED colour. The conditions are in `active_keys(ctx)` (ctx from `gather()`: DreamPi state, selected network, the web service's `net` file, Wi-Fi setup state, update status/info, reboot mark, DCNET problem). Aggregates: `error` (`ERRORS`: DreamPi not running, no network, no internet, under-voltage, over 80 °C, modem missing), `warning` (`WARNINGS`: DNS failing, slow connection, weak Wi-Fi, no IP yet, throttled, warm, failed Wi-Fi setup, failed update, update available), `ok` (neither); `off` is the fallback: it is used only when no other group is lit (`active_messages()`). `active_messages(ctx=None)` returns one look per lit group, lowest priority (bottom row) first, and the LED service draws them in that order (`leds` null = all, `[a, b]` = range, 1-based), so a higher row ends up on top. `players-game` / `players-friend` come from the players module's favorites through `core.players_watch()` / `ctx["players"]`. `dreampi_look()` is what the page's DreamPi dot previews (DreamPi state and selection only).
- **Event starting soon** (`event-soon`, announced by the events module): `gather()` asks `core.event_reminder()`, which reads `event_reminders.json` (written by the events module whenever reminders change and every minute by its background sync): a reminded event from `lead` minutes before its start until `after` (10) minutes after it, unless dismissed. So the LED shows it without the page being open. The default rows put it above *Ready for calls*, below the calls.
- **Default groups** (`default_groups()`, top row first): g1 red blinking (DreamPi not running), g2 yellow blinking (Starting up), g3 `network` solid (in a call DCNow! / DCNET), g4 purple solid (in a call, Netlink or other), g5 bright pink blinking (Event starting soon), g6 `network` solid (Ready for calls DCNow! / DCNET, DCNow! / DCNET selected). The optional messages are in no group until the user adds them. **Older files:** an `led.json` with a `"priority"` list (the message order of the earlier version) has its groups put in that order (`order_by_priority()`: a group takes the place of its most important message; the key is dropped on the next save), and the add-on's own old default groups (`_old_default_groups()`: DCNow! / DCNET / purple / yellow / red / pink with the selection and ready messages together) become the new defaults, because the old ones could only work with a separate message order. An older `led.json` with one look per message (`messages`, `colours`) is not carried over: it gets the default groups.
- **Signals added for the messages** (all measured off-hardware only, see [hardware-status.md](hardware-status.md)): the web service's `/tmp/dreampi-netswitch.net` now also has `dns_fail`, `no_ip`, `wifi_weak` (`probes.wifi_level()` from /proc/net/wireless, ≤ -75 dBm), `slow` (`probes.ping_quality()`/`is_slow()`: a ping every 30 s while the internet works, ≥ 200 ms average or ≥ 10 % loss), `modem`, `undervoltage`, `throttled`, `hot` (≥ 80 °C) and `warm` (≥ 70 °C). The update module writes `update_info` (`core.write_update_info()`: add-on / DreamPi update available) after each check and `core.mark_reboot()` before a reboot (`reboot_pending()` is true for 60 s). **Nothing checks for updates by itself**: the check runs only when the user presses Check now, so "update available" on the LED reflects the last manual check (kept in /tmp until the next reboot).
- **The page**: the colour rows are the standard `triggers` widget (see [modules.md](modules.md)) over `GET`/`POST /ledrows`: `netswitch_led_web._rows_reply()` writes each row's title ("Orange, solid"), its grey line (level, LEDs), its `look` (the row's buttons and tags take the colour through `editRow().setLook()`; a blinking look makes them run the `lkblink` animation between the colour and the default dark grey of a button; a row in the colour of the selected network follows the switch) and its `opts` (`colour`, `effect`, `speed`, `brightness`, `leds`), with the option controls (`colour`, `choice`, `slider` (logarithmic level, `null` = the global level), `range` (LEDs of a strip, only when the count is above 1)) and the `choices` (the announced messages, grouped, not in any row yet). Rows are dragged by their handle (`rules.sort`), **Add colour** adds a row (its starting options come from `new`) and opens its editor, **Restore defaults** posts the default rows. `modules/led/page.js` is only the custom widget `led-tools` (Calibration and Colours rows; its changes ask the rows to read their texts again, `reloadTriggers("/ledrows")`).
- Network colours (the switcher module's picks from the global palette, `base_core.py`): `PALETTE` = 15 named colours (and the switcher's own `network` after them, `colour_tokens()`) (id, name, hue group, page colour, lighter page colour, **LED colour**: the LED's own tuning, orange `#ff8c00`, blue `#0046ff`, red `#ff0000`, green `#00ff00`, the others and the `bright-` ones are estimates, not seen on a real LED); `module_colours("switcher")` = `{"dcnow": id, "dcnet": id}` (defaults orange / blue, `colours_unique`: picking the other's colour swaps them; `colours.json`), `network_colour(net)` the palette entry (orange / blue when the switcher is missing). The LED messages `ready/connecting/call` x `dcnow/dcnet` store the tokens `"dcnow"` / `"dcnet"` as their colour; `active_messages()` resolves them to the network's `led` hex, and a hex saved for such a message is ignored (`NET_BOUND`, sent to the page by `GET /ledconfig` as `net_bound` with `net_led`; the message table greys those colour inputs). The page side: the `swatches` widget, `POST /colour`, `GET /colours`. The red / green defaults are approximations of the Dreamcast BIOS buttons.
- LED/status colours: `/opt/dreampi-netswitch/led.json` = `{"max_brightness": 0..1 (default 0.08; the page slider is logarithmic, base 100, 0-1000 steps), "order": "GRB"|"RGB"|"RBG"|"GBR"|"BRG"|"BGR" (wire order, most WS2812s are GRB), "white_balance": {"r"|"g"|"b": 0..1, default 1.0 each}, "gamma": 0.5..4.0 (default `ledconfig.GAMMA` = 2.2, no page control - see Colour calibration below), "groups": [see above, the order is the priority]}` (a group's `brightness` null = use `max_brightness`, the global level that lives only in the Calibration pop-up; `active_messages()` returns the effective value, which the LED uses). `netswitch_ledconfig.led_config()` fills in defaults and validates; `save_led_config()` writes atomically (tmp + rename). `GET /ledconfig` returns the calibration (`config`: `max_brightness`, `white_balance`, `order`), `token_ui`, `count` and whether the LED count is above 0 (`installed`); `POST /ledconfig` takes `max_brightness` / `white_balance` / `gamma` and leaves the rows alone (those are `POST /ledrows`). `dreampi_look()` gives the current colour/blink; `/api` includes it as `dreampi.look`, and the page's DreamPi dot uses it (inline background + `blink` class), so the dot previews the LED (the dot is a flat CSS colour, so it doesn't itself run through gamma/white balance - only the physical LED does).
- Colour calibration (`netswitch_ledconfig.py`: `GAMMA`; `netswitch_led.py`: `to_bytes()`/`_wb()`): a simple NeoPixel-style pipeline, not a per-colour grid - **requested colour -> gamma correction -> white-balance multipliers -> max_brightness -> NeoPixel**, applied per channel in `to_bytes()`. Gamma (`x ** gamma`, 0..1 in, fixed 2.2, no UI - "not something the user normally needs to configure" per the user's request, though it's stored in led.json so a hand-edit can still tune it) compensates for the LED's duty-cycle brightness not matching perceived brightness: full-on is unchanged, dim values come out dimmer, which is also why it must run *before* white balance and brightness - those work on perceptually-linear values, and gamma is what makes them perceptually linear in the first place. White balance is a plain per-channel multiplier (`white_balance.r/g/b`, 0..1, 1.0 = no correction) found once, by eye, with the LED held at solid white (see below) and the R/G/B sliders in the Calibration pop-up of Settings > Status LED (which also holds the maximum-brightness slider, `#led-bright`) nudged down on whichever channel looks too strong, left at 255 otherwise (the sliders are 0-255 in a fixed grid, `.range.wb`, so all three are the same length; stored in led.json as value/255, 0..1) - deliberately not per-colour or per-brightness like the grid this replaced, since a flat multiplier already fixes a NeoPixel's usual white-balance tint (one channel's LED die running a bit brighter than the others) well enough, in about 30 seconds instead of calibrating dozens of swatches. `max_brightness` (the renamed "global brightness" slider) is applied last, after correction, so it scales the already-balanced colour rather than the raw request - exactly the "global output limit, independent of the requested colour" the user asked for.
- White-balance test: `#wb-preview` in the calibration pop-up (`#cal-pop`, opened by the Adjust button of the Calibration row in the Status LED box; closing the pop-up also ends the test hold) ("Preview on LED"/"Stop preview", turns white while active) toggles a live hold of the LED at solid white, run through the exact same pipeline being calibrated (so what's compared against "does this look neutral" is literally the calibrated output, not a separate preview mechanism) instead of its usual status effects. `POST /wbtest` (touches `WB_TEST` = `/tmp/dreampi-netswitch.wbtest`, a timestamp) while the toggle is on, with a 1 s heartbeat from `setWbPreview()` so a closed/crashed tab doesn't leave the LED stuck white; `POST /wbtestdone` turns it off, also sent automatically when Settings closes. `ledconfig.wb_test_active()` returns whether that file is fresher than `WB_TEST_STALE` (3 s). The LED service's main loop checks it every `REFRESH` tick alongside everything else it reads from the page, and while active shows `to_bytes([(1,1,1)]*count, max_brightness, white_balance, gamma)` directly instead of calling `render()`.

## Drivers and the LED service

`netswitch_led.py` (Python 3, service `dreampi-netswitch-led` running as root, installed and started whenever the module is present; `install.sh --leds=N` (0-300, just the *starting* count, stored in `/opt/dreampi-netswitch/led_count`, default 1 when the file is missing; `--led`, `--led=N` and `--no-led` are accepted aliases; the old `led_enabled` marker is deleted). Count 0 = no LEDs: the service idles (`switch_output()` returns no output and the loop just waits), `/ledconfig` reports `installed: false` and the page hides the Status LED section and the LED row of the GPIO card (the count / pin / wire order row is the LED row of the GPIO card, added through the `buttons_rows` slot). The page's count field starts at 1 so the page can't strand itself at 0; 0 is set at install (`--leds=0`) or by editing the file) drives WS2812s on one of four pins (`GPIO_PINS` = 10, 12, 18, 21; `DEFAULT_GPIO` = 18), stored in `/opt/dreampi-netswitch/led_gpio` (`install.sh --led-gpio=N`, also editable from the page) with no driver or Python package, except on GPIO10. GPIO12 and GPIO18 are the PWM0 peripheral (only the pin's ALT function differs: ALT0 vs ALT5); GPIO21 is the PCM peripheral (PCM_DOUT, ALT0), the same technique through different registers, used so GPIO12/18 (or the audio jack, which also uses PWM) stay free; GPIO10 is hardware SPI0 (MOSI) through the kernel's own `spidev` character device instead of `/dev/mem`, needing `dtparam=spi=on` (which `install.sh --led-gpio=10` adds to `/boot/firmware/config.txt` or `/boot/config.txt`, tracked in `spi_added` the same way the old SPI-on-GPIO10 versions were, so switching away removes it again; needs a reboot either way). For PWM/PCM: maps the GPIO, clock-manager and peripheral register blocks from `/dev/mem` (`base_gpio.peripheral_base()`, reading `/proc/device-tree/soc/ranges`; 32-bit accesses through `base_gpio.Block`, `ctypes.c_uint32.from_buffer` - that module is shared with `netswitch_buttons.py`'s button reading, each service opens its own `/dev/mem` mapping since they're separate processes), sets the pin's ALT function and clocks the peripheral from the crystal (19.2 MHz / 8 = 2.4 MHz; Pi 4: 54 MHz / 22) via `_init_clock()` (shared between PWM's and PCM's clock-generator offsets, `CM_PWMCTL`/`CM_PWMDIV` vs `CM_PCMCTL`/`CM_PCMDIV` - same register layout, BCM2835), serialiser mode, 3 output-clock ticks per LED bit (`100` = 0, `110` = 1), wire order from `led.json` (default GRB, matching the old hardcoded order), MSB first (`_TABLE` maps a byte to 3 bytes; `ORDERS` maps the 6 permutations to which of `(r, g, b)` goes out 1st/2nd/3rd, kept on the output object as `.order`).
- 1 LED on GPIO12/18 (`FifoPixel`): 3 words written straight into the FIFO; the pin idles low when it empties (`RPTL1` off), which latches.
- Anything else on GPIO12/18/21 (`DmaStrip` for PWM, `PcmStrip` for PCM, sharing `_DmaOutput`'s `show()`/close via `_dma_setup()`/`_dma_close()`): like rpi_ws281x. GPU memory from the VideoCore mailbox (`_alloc_gpu()`/`_free_gpu()`: `/dev/vcio`, `_IOWR(100,0,char*)`; tags 0x3000C alloc (flags 0x4 on Pi 2+, 0xC on Pi 1), 0x3000D lock -> bus address, 0x3000E/F unlock/release on exit), mapped through `/dev/mem` at `bus & ~0xC0000000`. Control block at offset 0 (TI = NO_WIDE_BURSTS|WAIT_RESP|DEST_DREQ|SRC_INC, PERMAP 5 for PWM's FIF1 (0x7E20C018) or 2 for PCM's fifo (0x7E203004)), data after it: the encoded stream byte-swapped per 32-bit word (both peripherals shift MSB first) plus 24 zero words (reset). DMA channel 10. PWM: PWM_DMAC = ENAB|PANIC 7|DREQ 3. PCM: `cs=EN`, `mode=FLEN(31)|FSLEN(1)`, `txc=CH1WEX|CH1EN|CH1POS(0)|CH1WID(8)`, `cs|=TXCLR`, `cs|=DMAEN`, `dreq=TX(0x3F)|TX_PANIC(0x10)`, `cs|=TXON` (register values cross-checked against github.com/jgarff/rpi_ws281x's pcm.h/ws2811.c, not from a datasheet or hardware). Each frame: wait for the channel, write data, reset channel, load CONBLK_AD, start.
- GPIO10 (`SpiStrip`): opens `/dev/spidevB.D` directly (mode/speed via `fcntl.ioctl`, no `spidev` package), ~6.4 MHz (the Pi rounds to 6.25 MHz). One whole SPI *byte* is one NeoPixel bit (`SPI_ONE`=0xF8, `SPI_ZERO`=0xC0, `_SPI_TABLE`), since spidev only deals in whole bytes; `show()` is a single blocking `os.write()`, no DMA. This is what the add-on's own older versions did on this exact pin (`git show 479cb3b:netswitch_led.py`), generalised here to any LED count, wire order and calibration.
- Single LED on GPIO18 verified on hardware; the DMA strip path (any peripheral/pin) only against fake memory/mailbox, and GPIO12/21/10 not at all.
- Engine (rebuilt from scratch; the effects are `solid`, `blink`, `fade`, `breathe`, `blink1` / `blink2` / `blink3` (short, double, triple blink) and `rainbow`, `EFFECTS` in `netswitch_ledconfig.py`, anything else in `led.json` is turned into the message's default effect): an effect is a function `(t, speed) -> level 0..1` in `EFFECT_LEVEL` (`_solid`, `_blink`: `BLINK_PERIOD` slow 1.0 s / fast 0.4 s, 50 % duty, starts lit); add an animation by adding a function and an `EFFECTS` entry. `render(messages, now, count, clocks, white_balance, gamma)` draws the messages in priority order into each one's LED section (a message in its dark half still owns its LEDs); each message's clock restarts when it appears or its look changes. Colour pipeline in `to_bytes()`: gamma -> white balance -> brightness -> `quantize()`. **`quantize()` keeps the hue**: the strongest channel is rounded, the others keep their ratio to it, a value too faint to light even one step is off; there is no dithering and no randomness, so the same input always gives the same bytes. (The old version forced every lit channel to at least 1 and dithered each channel on its own, which made a dimmed orange flicker and drift to green.) `Steady` (`HOLD` 0.4 s) holds the shown message list until a new one has stayed the same for that long, so a state flipping for a moment (DreamPi restarting) doesn't flash. A change the user makes is exempt: the main loop looks at `watched_files()` every frame (`os.stat` of the network flag, `led.json`, `palette.json`, `led_colours.json`, `palette_custom.json`, `colours.json`, `led_count`, `led_gpio`, `modules.json`, the white-balance test file; they are written in one go by a rename), and when one has changed it reads the state at once and calls `feed(..., immediate=True)`, so the LED follows a click on the page within a frame instead of the poll (`REFRESH` 0.25 s) plus the hold (0.4 s) that made a colour change take 0.7 s. Loop: 25 fps; reads `ledconfig.active_messages()` every 0.25 s; the frame is sent when it changes and at least every `KEEPALIVE` (3 s) so a glitch on the data line can't stay on the strip; hook state files are written atomically so a half-written file can't be read. The service asks for `SCHED_FIFO` (priority 1) at start, best effort (a failure is ignored). While white-balance testing it shows solid white through the same `to_bytes()`. The main loop also re-reads `ledconfig.led_config()` (`order`, `white_balance` via `_wb()`, `gamma`), `ledconfig.led_count()` and `ledconfig.led_gpio()` every 0.25 s; a changed count or pin opens the new hardware output *before* closing the old one (falls back to keeping the current output, logged to stderr, if the new one fails to open - e.g. GPIO10 chosen without SPI enabled) so the LED count and output pin can both be changed from the page without a restart. Tests: `tests/test_led_engine.py`, `tests/test_network_colours.py`.
- SPI for GPIO10 is set up by the service itself (`netswitch_led_spi.py`, `ensure_spi()`): when GPIO10 is the pin (at start, or when the page changes it) it adds `dtparam=spi=on  # added by dreampi-netswitch` to `/boot/firmware/config.txt` or `/boot/config.txt` (the file is recorded in `spi_added`, `core.SPI_ADDED`) unless an active `dtparam=spi=on` is already there, then tries `dtparam spi=on` and `modprobe spidev` so the device can appear without a reboot; when the pin moves away from GPIO10 it removes only that marked line (and tries `dtparam spi=off`). It is retried at most every 30 s while the device is missing (the output switch itself retries every 0.25 s and logs a failure once). `install.sh` calls `netswitch_led_spi.py sync` instead of editing config.txt itself; `remove.sh` and `uninstall.sh` still remove the marked line. The web service can't do this (its unit has `ProtectSystem=full`, so `/boot` is read-only for it), which is why the LED service does. Same idea older versions of the add-on used on this pin.

## Effects, per-colour calibration and Ready (added with the colour groups)

- **Effects** (`netswitch_led.py`): `PERIOD` = (slow, fast) seconds per round: blink 1 / 0.4, fade 3 / 1.2, breathe 4 / 1.6, short / double / triple blink 1.6 / 0.8, rainbow 6 / 2. `effect_level()` gives 0..1 (fade and breathe are a cosine, starting at 1; `BREATHE_LOW` = 0.12 is the dimmest breath; the flashes are `PULSE` = 9 % of the round long with a gap of the same length, then dark), `effect_colour()` only changes the colour for the rainbow (hue round the wheel). `NEVER_OFF` (breathe): when the 8-bit result would be (0, 0, 0) at a low brightness `render()` lights one step on the strongest channel instead, so a breath never goes dark (at 1 % that lowest step can look a little off in hue: the LED only takes whole numbers). Without dithering, a fade at a low maximum brightness has few steps. The page runs the same effects on the buttons and tags of a row (`page.css`, `lkblink` / `lkfade` / `lkb1..3` / `lkrainbow`, between the colour and the default grey; `editRow().setLook()`), and on the status dot (`DOT_FX` in `page.js`). A new effect needs: a name in `ledconfig.EFFECTS`, a period and a function in `netswitch_led.py`, and a keyframes + class in `page.css`; `tests/test_led_engine.py` checks that every effect of the page has a function and a period.
- **Ready for calls** is two messages, `ready-dcnow` and `ready-dcnet` (the one of the selected network is true); an older `led.json` with `ready` gets both (`OLD_KEYS`). A group in the colour token `network` (or `dcnow` / `dcnet`) follows the network switch: the LED reads the selection every 0.25 s, and `/api` has `led.tokens` (the three colours as they are now) so the rows in Settings follow it too.
- **Per-colour calibration:** the user sets how the LED shows each palette colour in Settings > Status LED > Colours: `GET`/`POST /ledcolours` (`{"id", "led"}` or `{"reset": id | "all"}`), kept in `led_colours.json` (`core.LED_COLOURS`; `core.set_led_colour()`, `reset_led_colours()`; `core.colours()` merges it over the palette; `led_default` is the shipped value, a colour of the user's own starts as its screen colour). How a colour looks on screen is the colour palette editor's (`palette.json`, `palette_custom.json`), the LED module only shows it. An older `palette.json` with `led` values still counts and is sorted into the two files by the next write. `led` is the colour asked for, before gamma, white balance and brightness. `POST /wbtest` takes `{"colour": "#rrggbb"}` (the LED holds that colour for 3 s, the page repeats it every second); no colour = white for the white balance (`wb_test_colour()`).

## Message priority

The priority is the order of the colour rows (`led.json` `groups`, top first): `active_messages()` ranks a group by its position (`rank = len(groups) - index`) and draws the groups lowest rank first, so the top row is on top. A separate message order (`"priority"`, `PRIORITY_ORDER`, `clean_priority()`) existed until the rows became the standard `triggers` widget; an older `led.json` that has it is migrated by `order_by_priority()` (see Default groups). The page sorts the rows with the base's `sortable()` (drag by the handle, arrow keys on it).

- **How fast a change shows:** the loop re-reads the state every `REFRESH` = 0.25 s and holds a changed message list for `Steady.HOLD` = 0.4 s so a half-finished transition (DreamPi starting a call) doesn't flicker. In addition `watched_state_files()` looks at the stamps of the files other programs write (DreamPi's state and active mark, the network, Wi-Fi setup, update status and info, the reboot mark, the players, the reminders) every frame; when one changed, the loop reads every `QUICK_REFRESH` = 0.05 s for `QUICK_WINDOW` = 0.6 s with a hold of `QUICK_HOLD` = 0.12 s, so a change shows about 0.2 s after the file was written (measured with a simulated LED driver, not on a Pi). Files the page writes (`watched_files()`) still show within a frame. How soon a file is written is up to its writer: the web service's `checker_step()` (0.5 s for cables, Wi-Fi, route and modem, 2 s for the Pi's health, 30 s / 5 s for the internet, or at once on `core.poke("internet")`), the players module (every 60 s), the hook (at once). Tested in `tests/test_poke.py`. **Sending the frame:** the loop sends a frame when it changed, **`BURST` = 6 times in a row** (one per loop, 40 ms apart), and an unchanged one every `KEEPALIVE` = 0.5 s (it was 3 s with a single send on a change). A frame that did not take on the real LED (not latched, garbled by a pre-emption) used to stay until the next keep-alive, which looks like a change that takes seconds; now the next copy follows within 40 ms. The loop's timing uses `time.monotonic()` (the Pi has no clock of its own and jumps when it finds the time on the network). With the debug log recording the service writes `LED: a change was shown N ms after a file changed`, and the journal gets a line when a round of the loop or a frame send takes over 0.3 s. Confirmed on a real Pi by the user: the change was slow before this and is fast again after it ([hardware-status.md](hardware-status.md)).
