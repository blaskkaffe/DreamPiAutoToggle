# Status LEDs, colours and calibration

Read before touching `netswitch_led.py`, `netswitch_led_drivers.py`, the LED settings in `netswitch_core.py` or the Status LED part of the page. Back to [CLAUDE.md](../CLAUDE.md).

## Messages, settings file and calibration

- LED messages: `LED_STATES` lists every message highest priority first with its category and defaults: category `wifi` (highest priority, see [Buttons and Wi-Fi setup](buttons-wifi.md)): `wifi-setup`, `wifi-ok`, `wifi-failed`; then errors `no-network`, `no-internet`, `pi`, `off`, `unknown`; information `busy`, `call-dcnow`, `call-dcnet`, `call`, `ok`, `ethernet`, `wifi` (the last two off by default; note the category "wifi" for the setup messages and the message key "wifi" for "Wi-Fi connected" are unrelated, unfortunate as that overlap is). `active_messages()` returns the enabled ones that apply now (DreamPi state + network state + `wifi_state()`, unless called with `wifi=False`), lowest priority first; the LED service's `render()` draws them in that order into each message's section (`leds` null = all, else [first, last] 1-based, clipped to the strip), so more important messages end up on top and uncovered LEDs stay dark. `status_look()` = the top one (currently unused; `api_state()` builds the dot preview straight from `active_messages()`). The page's DreamPi dot previews only the DreamPi-state message (`active_messages(state, {"network": True}, wifi=False)` - `wifi=False` so it never shows the Wi-Fi setup colour there, only in warning boxes and the real LED).
- LED/status colours: `/opt/dreampi-netswitch/led.json` = `{"max_brightness": 0..1 (default 0.08; the page slider is logarithmic, base 100, 0-1000 steps), "order": "GRB"|"RGB"|"RBG"|"GBR"|"BRG"|"BGR" (wire order, most WS2812s are GRB), "white_balance": {"r"|"g"|"b": 0..1, default 1.0 each}, "gamma": 0.5..4.0 (default `core.GAMMA` = 2.2, no page control - see Colour calibration below), "colours": {"dcnow"|"dcnet": {<state>: {"color": "#rrggbb", "effect": solid|blink|breathe|rgb|rainbow|scanner|comet|chase|twinkle, "speed": slow|fast, "brightness": null | 0..1, "enabled": bool, "leds": null | [first, last]}}}}` (per-status `brightness` null = use `max_brightness`; `status_look()` returns the effective value, which the LED uses), keyed by the *selected* network (`dcnet_mode`) and the `dreampi_state()` value. `netswitch_core.led_config()` fills in defaults and validates; `save_led_config()` writes atomically (tmp + rename). `GET /ledconfig` returns config, defaults, state labels, `orders`, whether `led_enabled` exists and whether `hidden` (see below); `POST /ledconfig` takes the whole config as JSON plus extra `count`/`gpio` fields (see Status NeoPixels) that aren't part of the saved JSON. `status_look()` gives the current colour/blink; `/api` includes it as `dreampi.look`, and the page's DreamPi dot uses it (inline background + `blink` class), so the dot previews the LED (the dot is a flat CSS colour, so it doesn't itself run through gamma/white balance - only the physical LED does).
- Colour calibration (`netswitch_core.py`: `GAMMA`; `netswitch_led.py`: `to_bytes()`/`_wb()`): a simple NeoPixel-style pipeline, not a per-colour grid - **requested colour -> gamma correction -> white-balance multipliers -> max_brightness -> NeoPixel**, applied per channel in `to_bytes()`. Gamma (`x ** gamma`, 0..1 in, fixed 2.2, no UI - "not something the user normally needs to configure" per the user's request, though it's stored in led.json so a hand-edit can still tune it) compensates for the LED's duty-cycle brightness not matching perceived brightness: full-on is unchanged, dim values come out dimmer, which is also why it must run *before* white balance and brightness - those work on perceptually-linear values, and gamma is what makes them perceptually linear in the first place. White balance is a plain per-channel multiplier (`white_balance.r/g/b`, 0..1, 1.0 = no correction) found once, by eye, with the LED held at solid white (see below) and the R/G/B sliders in Settings > Status LED nudged down on whichever channel looks too strong, left at 255 otherwise (the sliders are 0-255 in a fixed grid, `.range.wb`, so all three are the same length; stored in led.json as value/255, 0..1) - deliberately not per-colour or per-brightness like the grid this replaced, since a flat multiplier already fixes a NeoPixel's usual white-balance tint (one channel's LED die running a bit brighter than the others) well enough, in about 30 seconds instead of calibrating dozens of swatches. `max_brightness` (the renamed "global brightness" slider) is applied last, after correction, so it scales the already-balanced colour rather than the raw request - exactly the "global output limit, independent of the requested colour" the user asked for.
- White-balance test: `#wb-preview` in Settings ("Preview on LED"/"Stop preview", turns white while active) toggles a live hold of the LED at solid white, run through the exact same pipeline being calibrated (so what's compared against "does this look neutral" is literally the calibrated output, not a separate preview mechanism) instead of its usual status effects. `POST /wbtest` (touches `WB_TEST` = `/tmp/dreampi-netswitch.wbtest`, a timestamp) while the toggle is on, with a 1 s heartbeat from `setWbPreview()` so a closed/crashed tab doesn't leave the LED stuck white; `POST /wbtestdone` turns it off, also sent automatically when Settings closes. `core.wb_test_active()` returns whether that file is fresher than `WB_TEST_STALE` (3 s). The LED service's main loop checks it every `REFRESH` tick alongside everything else it reads from the page, and while active shows `to_bytes([(1,1,1)]*count, max_brightness, white_balance, gamma, dither=False)` directly instead of calling `render()`.
- Hiding the LED settings: `/opt/dreampi-netswitch/led_hidden` (exists = hidden), toggled by `POST /ledhide` from a "Hide" button inside `#led-section` (with a confirm dialog, since there is no way back from the page itself - the button that hides the section is inside the section it hides). Meant for shipping a product with the LEDs already configured and keeping end users from changing them by accident; only reversible by deleting the file on the Pi (or reinstalling). `loadLed()` hides `#led-section` when either `installed` is false or `hidden` is true.

## Drivers and the LED service

`netswitch_led.py` (Python 3, service `dreampi-netswitch-led` running as root, installed with `install.sh --led` or `--led=N` (1-300, just the *starting* count, stored in `/opt/dreampi-netswitch/led_count`), remembered via `led_enabled`, removed with `--no-led`) drives WS2812s on one of four pins (`GPIO_PINS` = 10, 12, 18, 21; `DEFAULT_GPIO` = 18), stored in `/opt/dreampi-netswitch/led_gpio` (`install.sh --led-gpio=N`, also editable from the page) with no driver or Python package, except on GPIO10. GPIO12 and GPIO18 are the PWM0 peripheral (only the pin's ALT function differs: ALT0 vs ALT5); GPIO21 is the PCM peripheral (PCM_DOUT, ALT0), the same technique through different registers, used so GPIO12/18 (or the audio jack, which also uses PWM) stay free; GPIO10 is hardware SPI0 (MOSI) through the kernel's own `spidev` character device instead of `/dev/mem`, needing `dtparam=spi=on` (which `install.sh --led-gpio=10` adds to `/boot/firmware/config.txt` or `/boot/config.txt`, tracked in `spi_added` the same way the old SPI-on-GPIO10 versions were, so switching away removes it again; needs a reboot either way). For PWM/PCM: maps the GPIO, clock-manager and peripheral register blocks from `/dev/mem` (`netswitch_gpio.peripheral_base()`, reading `/proc/device-tree/soc/ranges`; 32-bit accesses through `netswitch_gpio.Block`, `ctypes.c_uint32.from_buffer` - that module is shared with `netswitch_buttons.py`'s button reading, each service opens its own `/dev/mem` mapping since they're separate processes), sets the pin's ALT function and clocks the peripheral from the crystal (19.2 MHz / 8 = 2.4 MHz; Pi 4: 54 MHz / 22) via `_init_clock()` (shared between PWM's and PCM's clock-generator offsets, `CM_PWMCTL`/`CM_PWMDIV` vs `CM_PCMCTL`/`CM_PCMDIV` - same register layout, BCM2835), serialiser mode, 3 output-clock ticks per LED bit (`100` = 0, `110` = 1), wire order from `led.json` (default GRB, matching the old hardcoded order), MSB first (`_TABLE` maps a byte to 3 bytes; `ORDERS` maps the 6 permutations to which of `(r, g, b)` goes out 1st/2nd/3rd, kept on the output object as `.order`).
- 1 LED on GPIO12/18 (`FifoPixel`): 3 words written straight into the FIFO; the pin idles low when it empties (`RPTL1` off), which latches.
- Anything else on GPIO12/18/21 (`DmaStrip` for PWM, `PcmStrip` for PCM, sharing `_DmaOutput`'s `show()`/close via `_dma_setup()`/`_dma_close()`): like rpi_ws281x. GPU memory from the VideoCore mailbox (`_alloc_gpu()`/`_free_gpu()`: `/dev/vcio`, `_IOWR(100,0,char*)`; tags 0x3000C alloc (flags 0x4 on Pi 2+, 0xC on Pi 1), 0x3000D lock -> bus address, 0x3000E/F unlock/release on exit), mapped through `/dev/mem` at `bus & ~0xC0000000`. Control block at offset 0 (TI = NO_WIDE_BURSTS|WAIT_RESP|DEST_DREQ|SRC_INC, PERMAP 5 for PWM's FIF1 (0x7E20C018) or 2 for PCM's fifo (0x7E203004)), data after it: the encoded stream byte-swapped per 32-bit word (both peripherals shift MSB first) plus 24 zero words (reset). DMA channel 10. PWM: PWM_DMAC = ENAB|PANIC 7|DREQ 3. PCM: `cs=EN`, `mode=FLEN(31)|FSLEN(1)`, `txc=CH1WEX|CH1EN|CH1POS(0)|CH1WID(8)`, `cs|=TXCLR`, `cs|=DMAEN`, `dreq=TX(0x3F)|TX_PANIC(0x10)`, `cs|=TXON` (register values cross-checked against github.com/jgarff/rpi_ws281x's pcm.h/ws2811.c, not from a datasheet or hardware). Each frame: wait for the channel, write data, reset channel, load CONBLK_AD, start.
- GPIO10 (`SpiStrip`): opens `/dev/spidevB.D` directly (mode/speed via `fcntl.ioctl`, no `spidev` package), ~6.4 MHz (the Pi rounds to 6.25 MHz). One whole SPI *byte* is one NeoPixel bit (`SPI_ONE`=0xF8, `SPI_ZERO`=0xC0, `_SPI_TABLE`), since spidev only deals in whole bytes; `show()` is a single blocking `os.write()`, no DMA. This is what the add-on's own older versions did on this exact pin (`git show 479cb3b:netswitch_led.py`), generalised here to any LED count, wire order and calibration.
- Single LED on GPIO18 verified on hardware; the DMA strip path (any peripheral/pin) only against fake memory/mailbox, and GPIO12/21/10 not at all.
- Loop: 50 fps; re-reads `core.wb_test_active()` and `core.active_messages()` every 0.25 s and, unless white-balance testing (see Colour calibration above), composes the messages with `render(messages, now, count, clocks, white_balance, gamma)`. Each message's effect restarts at t=0 when it appears or its look changes (`clocks`), so blink starts lit and breathe starts bright. Unchanged frames are only resent every 0.5 s (CPU). The service runs at Nice=10. `effect_frame(effect, speed, colour, t, n)` gives floats per LED; `to_bytes()` applies gamma, white balance and brightness in that order (see Colour calibration above), then quantizes to 0..255 with temporal (error-diffusion) dithering: the rounding error is carried over per (LED index, channel) and added to the next frame, so a value 8-bit output can't represent exactly - the normal case at low brightness, where slow effects like breathe would otherwise visibly step between levels - is approximated by alternating the neighbouring levels over time instead of always rounding the same way; `reset_dither()` clears that carried-over state. The main loop also re-reads `core.led_config()` (`order`, `white_balance` via `_wb()`, `gamma`), `core.led_count()` and `core.led_gpio()` every 0.25 s; a changed count or pin opens the new hardware output *before* closing the old one (falls back to keeping the current output, logged to stderr, if the new one fails to open - e.g. GPIO10 chosen without SPI enabled) so the LED count and output pin can both be changed from the page without a restart, and a failed switch can't leave the service stuck on a closed output. Effects: solid, blink, breathe, rgb (20 s slow / 10 s fast; rainbow the same) for any count; rainbow, scanner, comet, chase, twinkle for strips (on 1 LED they fall back to rgb/breathe/blink-like output). Periods per effect in `PERIODS` (slow, fast).
- Older versions used SPI on GPIO10 and added `dtparam=spi=on  # added by dreampi-netswitch` (recorded in `spi_added`); the installer and uninstaller remove only that line - the current SPI path (`SpiStrip`, above) is the same idea, generalised to any LED count/order/calibration.
