# Status LEDs, colours and calibration

Read before touching `netswitch_led.py`, `netswitch_led_drivers.py`, the LED settings in `netswitch_ledconfig.py` or the Status LED part of the page. Back to [CLAUDE.md](../CLAUDE.md).

## Messages, settings file and calibration

- LED messages: `LED_STATES` lists every message in the order the page shows them: `(key, label, group, colour, effect, speed, enabled, detected)`, `GROUPS` the headings (System, Network, Call — DCNow!, Call — DCNET, Call — Netlink, Wi-Fi setup). The messages are independent: no per-network tables; many share a default look on purpose. Colour semantics: ORANGE `#ff8c00` = DCNow!, BLUE `#0046ff` = DCNET, PURPLE `#aa00ff` = Netlink, RED = fault (failed calls are red, never the network colour), AMBER `#ffd000` = warning/starting; the orange is chosen so that *after gamma* (2.2 is applied to every channel) it stays well away from red and amber (`tests/test_led_messages.py` checks the hues). `PRIORITY_ORDER` is the priority (highest first, separate from the display order): Wi-Fi setup, no-network, no-internet, pi, off, failed-*, net-switch, busy, call-*, connecting-*, ready-*, ethernet, wifi, unknown. `active_messages()` returns the enabled ones that apply now, lowest priority first (state via `message_for_state()`: `ok` -> `ready-dcnet`/`ready-dcnow` by the selected network, `call` (any DreamPi call that isn't DCNow!/DCNET) -> `call-netlink`; plus `wifi_state()` unless `wifi=False`); a disabled message gives nothing; **`unknown` is dropped as soon as any other enabled message applies**. The LED service's `render()` draws them in that order into each message's section (`leds` null = all, `[n, n]` = one LED, `[a, b]` = range, 1-based, clipped to the strip), so several messages can show at once on different LEDs and more important ones end up on top. **`detected` False** (`net-switch`, `connecting-*`, `failed-*`, `ready-netlink`): the page can configure them, but nothing in `dreampi_state()`/the network state says when they happen (DreamPi's state file only has starting / ready / call <kind>; Netlink isn't selectable; nothing marks a network switch), so they never appear - deliberately not faked. The DreamPi log lines the hook already parses ("Call answered", "Connected", "Couldn't answer call", "Switched to ...") could drive them later. `status_look()` = the top one (unused; `api_state()` builds the dot preview from `active_messages()`). The page's DreamPi dot previews only the DreamPi-state message (`wifi=False`).
- Ping effect (`netswitch_led.ping_level()`, `PING`): per speed (slow / fast) first pulse, gap, second pulse, pause = 0.14 / 0.12 / 0.14 / 1.10 s and 0.10 / 0.08 / 0.10 / 0.70 s; a pulse rises over `PING_RISE` (30 %) of its length and fades over the rest. Every LED of the message pulses together (so one LED of a strip, a range or all work the same) through the normal pipeline: gamma, white balance, then the message's own level or the global brightness. The page's dot previews it with the `ping` CSS keyframes. Not seen on a real LED yet.
- LED/status colours: `/opt/dreampi-netswitch/led.json` = `{"max_brightness": 0..1 (default 0.08; the page slider is logarithmic, base 100, 0-1000 steps), "order": "GRB"|"RGB"|"RBG"|"GBR"|"BRG"|"BGR" (wire order, most WS2812s are GRB), "white_balance": {"r"|"g"|"b": 0..1, default 1.0 each}, "gamma": 0.5..4.0 (default `ledconfig.GAMMA` = 2.2, no page control - see Colour calibration below), "messages": {<message key>: {"color": "#rrggbb", "effect": solid|blink|breathe|ping|rgb|rainbow|scanner|comet|chase|twinkle, "speed": slow|fast, "brightness": null | 0..1, "enabled": bool, "leds": null | [first, last]}}}` (per-message `brightness` null = use `max_brightness`, the global level that lives only in NeoPixel calibration; `active_messages()` returns the effective value, which the LED uses). **Older files** had `"colours": {"dcnow"|"dcnet": {<old state>: ...}}` (one table per selected network): `clean_led_config()` still reads that when there is no `messages` (`_legacy_entry()`: an old entry is carried over only if it differs from its old default - `ok` -> `ready-dcnow`/`ready-dcnet` from the matching table, `call` -> `call-netlink`, the rest from the DCNow! table first, then DCNET's - otherwise the message gets the new default look) and never writes `colours` again. `netswitch_ledconfig.led_config()` fills in defaults and validates; `save_led_config()` writes atomically (tmp + rename). `GET /ledconfig` returns config, defaults, `states` (`LED_STATES`), `groups`, `effects`, `orders`, whether the LED count is above 0 (`installed`) and whether `hidden` (see below); `POST /ledconfig` takes the whole config as JSON plus extra `count`/`gpio` fields (see Status NeoPixels) that aren't part of the saved JSON. `status_look()` gives the current colour/blink; `/api` includes it as `dreampi.look`, and the page's DreamPi dot uses it (inline background + `blink` class), so the dot previews the LED (the dot is a flat CSS colour, so it doesn't itself run through gamma/white balance - only the physical LED does).
- Colour calibration (`netswitch_ledconfig.py`: `GAMMA`; `netswitch_led.py`: `to_bytes()`/`_wb()`): a simple NeoPixel-style pipeline, not a per-colour grid - **requested colour -> gamma correction -> white-balance multipliers -> max_brightness -> NeoPixel**, applied per channel in `to_bytes()`. Gamma (`x ** gamma`, 0..1 in, fixed 2.2, no UI - "not something the user normally needs to configure" per the user's request, though it's stored in led.json so a hand-edit can still tune it) compensates for the LED's duty-cycle brightness not matching perceived brightness: full-on is unchanged, dim values come out dimmer, which is also why it must run *before* white balance and brightness - those work on perceptually-linear values, and gamma is what makes them perceptually linear in the first place. White balance is a plain per-channel multiplier (`white_balance.r/g/b`, 0..1, 1.0 = no correction) found once, by eye, with the LED held at solid white (see below) and the R/G/B sliders in Settings > NeoPixel calibration (which also holds the maximum-brightness slider, `#led-bright`) nudged down on whichever channel looks too strong, left at 255 otherwise (the sliders are 0-255 in a fixed grid, `.range.wb`, so all three are the same length; stored in led.json as value/255, 0..1) - deliberately not per-colour or per-brightness like the grid this replaced, since a flat multiplier already fixes a NeoPixel's usual white-balance tint (one channel's LED die running a bit brighter than the others) well enough, in about 30 seconds instead of calibrating dozens of swatches. `max_brightness` (the renamed "global brightness" slider) is applied last, after correction, so it scales the already-balanced colour rather than the raw request - exactly the "global output limit, independent of the requested colour" the user asked for.
- White-balance test: `#wb-preview` in Settings ("Preview on LED"/"Stop preview", turns white while active) toggles a live hold of the LED at solid white, run through the exact same pipeline being calibrated (so what's compared against "does this look neutral" is literally the calibrated output, not a separate preview mechanism) instead of its usual status effects. `POST /wbtest` (touches `WB_TEST` = `/tmp/dreampi-netswitch.wbtest`, a timestamp) while the toggle is on, with a 1 s heartbeat from `setWbPreview()` so a closed/crashed tab doesn't leave the LED stuck white; `POST /wbtestdone` turns it off, also sent automatically when Settings closes. `ledconfig.wb_test_active()` returns whether that file is fresher than `WB_TEST_STALE` (3 s). The LED service's main loop checks it every `REFRESH` tick alongside everything else it reads from the page, and while active shows `to_bytes([(1,1,1)]*count, max_brightness, white_balance, gamma, dither=False)` directly instead of calling `render()`.
- Hiding the LED settings: `/opt/dreampi-netswitch/led_hidden` (exists = hidden), toggled by `POST /ledhide` from a "Hide" button inside `#led-section` (with a confirm dialog, since there is no way back from the page itself - the button that hides the section is inside the section it hides). Meant for shipping a product with the LEDs already configured and keeping end users from changing them by accident; only reversible by deleting the file on the Pi (or reinstalling). `loadLed()` hides `#led-section` when either `installed` is false or `hidden` is true.

## Drivers and the LED service

`netswitch_led.py` (Python 3, service `dreampi-netswitch-led` running as root, always installed and started; `install.sh --leds=N` (0-300, just the *starting* count, stored in `/opt/dreampi-netswitch/led_count`, default 1 when the file is missing; `--led`, `--led=N` and `--no-led` are accepted aliases; the old `led_enabled` marker is deleted). Count 0 = no LEDs: the service idles (`switch_output()` returns no output and the loop just waits), `/ledconfig` reports `installed: false` and the page hides the NeoPixel calibration + Status LED sections and the GPIO LED row. The page's count field starts at 1 so the page can't strand itself at 0; 0 is set at install (`--leds=0`) or by editing the file) drives WS2812s on one of four pins (`GPIO_PINS` = 10, 12, 18, 21; `DEFAULT_GPIO` = 18), stored in `/opt/dreampi-netswitch/led_gpio` (`install.sh --led-gpio=N`, also editable from the page) with no driver or Python package, except on GPIO10. GPIO12 and GPIO18 are the PWM0 peripheral (only the pin's ALT function differs: ALT0 vs ALT5); GPIO21 is the PCM peripheral (PCM_DOUT, ALT0), the same technique through different registers, used so GPIO12/18 (or the audio jack, which also uses PWM) stay free; GPIO10 is hardware SPI0 (MOSI) through the kernel's own `spidev` character device instead of `/dev/mem`, needing `dtparam=spi=on` (which `install.sh --led-gpio=10` adds to `/boot/firmware/config.txt` or `/boot/config.txt`, tracked in `spi_added` the same way the old SPI-on-GPIO10 versions were, so switching away removes it again; needs a reboot either way). For PWM/PCM: maps the GPIO, clock-manager and peripheral register blocks from `/dev/mem` (`netswitch_gpio.peripheral_base()`, reading `/proc/device-tree/soc/ranges`; 32-bit accesses through `netswitch_gpio.Block`, `ctypes.c_uint32.from_buffer` - that module is shared with `netswitch_buttons.py`'s button reading, each service opens its own `/dev/mem` mapping since they're separate processes), sets the pin's ALT function and clocks the peripheral from the crystal (19.2 MHz / 8 = 2.4 MHz; Pi 4: 54 MHz / 22) via `_init_clock()` (shared between PWM's and PCM's clock-generator offsets, `CM_PWMCTL`/`CM_PWMDIV` vs `CM_PCMCTL`/`CM_PCMDIV` - same register layout, BCM2835), serialiser mode, 3 output-clock ticks per LED bit (`100` = 0, `110` = 1), wire order from `led.json` (default GRB, matching the old hardcoded order), MSB first (`_TABLE` maps a byte to 3 bytes; `ORDERS` maps the 6 permutations to which of `(r, g, b)` goes out 1st/2nd/3rd, kept on the output object as `.order`).
- 1 LED on GPIO12/18 (`FifoPixel`): 3 words written straight into the FIFO; the pin idles low when it empties (`RPTL1` off), which latches.
- Anything else on GPIO12/18/21 (`DmaStrip` for PWM, `PcmStrip` for PCM, sharing `_DmaOutput`'s `show()`/close via `_dma_setup()`/`_dma_close()`): like rpi_ws281x. GPU memory from the VideoCore mailbox (`_alloc_gpu()`/`_free_gpu()`: `/dev/vcio`, `_IOWR(100,0,char*)`; tags 0x3000C alloc (flags 0x4 on Pi 2+, 0xC on Pi 1), 0x3000D lock -> bus address, 0x3000E/F unlock/release on exit), mapped through `/dev/mem` at `bus & ~0xC0000000`. Control block at offset 0 (TI = NO_WIDE_BURSTS|WAIT_RESP|DEST_DREQ|SRC_INC, PERMAP 5 for PWM's FIF1 (0x7E20C018) or 2 for PCM's fifo (0x7E203004)), data after it: the encoded stream byte-swapped per 32-bit word (both peripherals shift MSB first) plus 24 zero words (reset). DMA channel 10. PWM: PWM_DMAC = ENAB|PANIC 7|DREQ 3. PCM: `cs=EN`, `mode=FLEN(31)|FSLEN(1)`, `txc=CH1WEX|CH1EN|CH1POS(0)|CH1WID(8)`, `cs|=TXCLR`, `cs|=DMAEN`, `dreq=TX(0x3F)|TX_PANIC(0x10)`, `cs|=TXON` (register values cross-checked against github.com/jgarff/rpi_ws281x's pcm.h/ws2811.c, not from a datasheet or hardware). Each frame: wait for the channel, write data, reset channel, load CONBLK_AD, start.
- GPIO10 (`SpiStrip`): opens `/dev/spidevB.D` directly (mode/speed via `fcntl.ioctl`, no `spidev` package), ~6.4 MHz (the Pi rounds to 6.25 MHz). One whole SPI *byte* is one NeoPixel bit (`SPI_ONE`=0xF8, `SPI_ZERO`=0xC0, `_SPI_TABLE`), since spidev only deals in whole bytes; `show()` is a single blocking `os.write()`, no DMA. This is what the add-on's own older versions did on this exact pin (`git show 479cb3b:netswitch_led.py`), generalised here to any LED count, wire order and calibration.
- Single LED on GPIO18 verified on hardware; the DMA strip path (any peripheral/pin) only against fake memory/mailbox, and GPIO12/21/10 not at all.
- Loop: 50 fps; re-reads `ledconfig.wb_test_active()` and `ledconfig.active_messages()` every 0.25 s and, unless white-balance testing (see Colour calibration above), composes the messages with `render(messages, now, count, clocks, white_balance, gamma)`. Each message's effect restarts at t=0 when it appears or its look changes (`clocks`), so blink starts lit and breathe starts bright. Unchanged frames are only resent every 0.5 s (CPU). The service runs at Nice=10. `effect_frame(effect, speed, colour, t, n)` gives floats per LED; `to_bytes()` applies gamma, white balance and brightness in that order (see Colour calibration above), then quantizes to 0..255 with temporal (error-diffusion) dithering: the rounding error is carried over per (LED index, channel) and added to the next frame, so a value 8-bit output can't represent exactly - the normal case at low brightness, where slow effects like breathe would otherwise visibly step between levels - is approximated by alternating the neighbouring levels over time instead of always rounding the same way; `reset_dither()` clears that carried-over state. The main loop also re-reads `ledconfig.led_config()` (`order`, `white_balance` via `_wb()`, `gamma`), `ledconfig.led_count()` and `ledconfig.led_gpio()` every 0.25 s; a changed count or pin opens the new hardware output *before* closing the old one (falls back to keeping the current output, logged to stderr, if the new one fails to open - e.g. GPIO10 chosen without SPI enabled) so the LED count and output pin can both be changed from the page without a restart, and a failed switch can't leave the service stuck on a closed output. Effects: solid, blink, breathe, rgb (20 s slow / 10 s fast; rainbow the same) for any count; rainbow, scanner, comet, chase, twinkle for strips (on 1 LED they fall back to rgb/breathe/blink-like output). Periods per effect in `PERIODS` (slow, fast).
- Older versions used SPI on GPIO10 and added `dtparam=spi=on  # added by dreampi-netswitch` (recorded in `spi_added`); the installer and uninstaller remove only that line - the current SPI path (`SpiStrip`, above) is the same idea, generalised to any LED count/order/calibration.
